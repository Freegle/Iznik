# Maintaining this documentation

The point of this folder is documentation that stays **true** as the product changes.
That only works if everyone follows a few conventions. They are deliberately light.

## Principles

1. **Docs live next to code and change with it.** If a pull request changes behaviour a
   doc describes, update the doc in the same pull request. Reviewers should be able to
   see the UI change and its documentation together.
2. **Plain Markdown, no build step.** GitHub renders these folders directly, so diffs are
   readable and screenshots review inline. We have deliberately *not* adopted a static
   site generator (Docusaurus, VitePress, Starlight) yet. Revisit that only when volume,
   search or versioning justifies the extra machinery.
3. **Orientation, not duplication, for developers.** The code and the reference docs at
   the repo root are the source of truth. Developer pages point at them. Do not copy code
   or long reference material into `docs/` where it will drift.
4. **No confidential material in `ops/`.** No secrets, credentials, API keys, tokens, IP
   addresses or private hostnames. Describe architecture and process only. If you are
   unsure, leave it out and link to the internal source instead.
5. **Write in plain English.** Short sentences. Hyphens, never em dashes.

## Structure

```
docs/
  README.md              index and glossary
  maintaining-docs.md    this file
  members/               four task guides + assets/ screenshots
  moderators/            four task guides + assets/ screenshots
  developers/            orientation pages that link into the code
  ops/                   architecture-level operational pages + runbooks/
  screenshots/           how the screenshot automation works
```

The **members** and **moderators** sections each have four numbered guides plus a
`README.md` index. Keep that shape. If a topic does not fit the four guides, add a
section to the closest one rather than proliferating files.

## Front matter

Every page starts with:

```yaml
---
last_reviewed: YYYY-MM-DD
owner: <team or role>
---
```

`last_reviewed` makes staleness visible. When you touch a page, bump it. A CI lint can
later flag pages whose `last_reviewed` predates the last change to the code they
document (see "Keeping it fresh" below).

## Adding or changing a page

1. Put the page in the right audience folder.
2. Add front matter and link it from that folder's `README.md`.
3. If it needs a screenshot, add an entry to the screenshot manifest rather than pasting
   an image by hand - see [screenshots/README.md](screenshots/README.md).
4. Cross-link related pages with relative links so navigation works on GitHub.

## Screenshots

Screenshots are **generated by Playwright driving the real app**, so they update the same
way the app does. Never paste in a manually captured image for a member or moderator
guide - add it to the manifest so it can be regenerated deterministically. Full detail,
including how to run it and how to keep shots stable, is in
[screenshots/README.md](screenshots/README.md).

Images are committed next to the guide that uses them, under `members/assets/`,
`moderators/assets/`, and so on.

## Keeping it fresh (recommended CI additions)

These are the practices that stop docs rotting. Adopt them as capacity allows:

1. **Screenshot drift gate.** On a pull request that touches `iznik-nuxt3/pages/`,
   `iznik-nuxt3/components/` or `iznik-nuxt3/modtools/`, regenerate the screenshots and
   fail the check if they differ beyond a small pixel threshold. This ties a doc update
   to the same pull request that changed the UI, exactly as the CircleCI orb version
   bumps already work. Do not silently auto-commit regenerated images - make a human look.
2. **Link checking.** Run a Markdown link checker (for example `lychee`) over `docs/` in
   CI to catch dead internal and external links cheaply.
3. **`last_reviewed` lint.** A few lines of Node can flag pages whose `last_reviewed` is
   older than the last commit touching the code they reference.
4. **CODEOWNERS.** Map `docs/members/**` and `docs/moderators/**` to the people who own
   the matching UI, so any pull request that changes it pings a docs reviewer.
5. **Step tests for the top journeys.** For a handful of critical walkthroughs (report a
   post, approve a member, post an OFFER), let a Playwright test assert the documented
   steps still work, so broken *steps*, not just stale images, get caught.
