# Existing FreegleDocker Intake/Ticketing Machinery

## What does monitor-fsm do (states, sources, outputs)?

### Takeaway
monitor-fsm is an unattended, FSM-driven loop (built on the `ai-flower` workflow engine) that pulls bug/error reports from two sources — Discourse forum topics and Sentry issues — triages them, attempts automated diagnosis and fixes, and produces pull requests plus Discourse replies; all state is persisted in a local SQLite file, `monitor.db`.

### Cited Findings
- monitor-fsm is described in its README as an automated bug-report-to-fix loop running on the `ai-flower` workflow engine — [monitor-fsm/README.md](/home/edward/FreegleDockerWSL/monitor-fsm/README.md)
- State is persisted in `monitor.db` (SQLite); tables present: `discourse_bug`, `discourse_draft`, `sentry_issue`, `pr`, `reviewer_feedback`, `topic_cursor`, `excluded_topics`, `iteration`, `kv`, `schema_version` — [monitor-fsm/monitor.db schema, this session](/home/edward/FreegleDockerWSL/monitor-fsm/monitor.db)
- `discourse_bug.state` is a CHECK-constrained enum: `open, investigating, fix-queued, deferred, fixed, confirmed, off-topic, duplicate, feature-request, question, needs-detail` — [monitor-fsm/monitor.db schema](/home/edward/FreegleDockerWSL/monitor-fsm/monitor.db)
- `sentry_issue.disposition` is a CHECK-constrained enum: `pending, investigating, ignored, fix-queued, fixed, deferred`, with `project` restricted to `'nuxt3'` or `'go'` — [monitor-fsm/monitor.db schema](/home/edward/FreegleDockerWSL/monitor-fsm/monitor.db)
- Workflow states named in `monitor-fsm/workflow.json` include `LOAD_STATE`, `CHECK_CI`, `DIAGNOSE_BUG`, `REPRODUCE_BUG`, `IMPLEMENT_FIX`, `VERIFY_DISCOURSE_BATCH`, `FIX_SENTRY_ISSUE`, `WRAP_UP` (among others) — [monitor-fsm/workflow.json](/home/edward/FreegleDockerWSL/monitor-fsm/workflow.json)
- It opens pull requests and runs its own adversarial review — [.claude/rules/monitor-fsm.md](/home/edward/FreegleDockerWSL/.claude/rules/monitor-fsm.md)
- It has exactly two permitted kinds of Discourse output: a verbatim "possible fix applied, please retest" reply once a fix is confirmed live, and a clarifying question asking the reporter for missing detail (which member, group, post, screenshot) — [memory: feedback_fsm_may_post_to_clarify]
- `PARSE_ONLY` does not stop tool nodes from continuing into dispatching fixes; confirm from the run log, not the flag — [.claude/rules/monitor-fsm.md](/home/edward/FreegleDockerWSL/.claude/rules/monitor-fsm.md)

### Inferences
- monitor-fsm is the closest thing Freegle has to an automated intake+triage+fix pipeline, but its scope is code-fix triage of forum/error reports, not general customer support.
- The `discourse_bug.state` enum conflates report *type* (`feature-request`, `question`, `duplicate`) with progress *state* (`investigating`, `fix-queued`, `fixed`) in a single column — there is no separate classification vs. lifecycle-status field.

### Gaps
- The exact source-selection/polling mechanism (how it decides which Discourse categories or Sentry projects to scan each lap) was not traced into the workflow/prompt code in this pass — only the state names and the SQLite schema were inspected directly.

## Is there anything in iznik-server-go, iznik-batch, or iznik-nuxt3/modtools modeling support tickets, chat-to-support, contact-volunteers, support@ mailbox handling, or admin support tooling?

### Takeaway
No genuine backend "support ticket" data model exists anywhere in iznik-server-go, iznik-batch, or iznik-nuxt3/modtools. The closest things are (a) a client-side mailto-link convention that embeds the logged-in member's user id into an email to support@, and (b) the AI Support Helper — a volunteer-facing chat tool inside ModTools that investigates one member at a time and can escalate by email, but keeps no server-side ticket/case record of its own.

### Cited Findings
- An exhaustive grep across `iznik-server-go`, `iznik-batch`, and `iznik-nuxt3`/`modtools` for `ticket`/`helpdesk`/`triage` turned up only false positives (reserved usernames, image-label categories, job-title mappings, literal event/raffle tickets) — [grep results, this session]
- `iznik-nuxt3/components/SupportLink.vue` renders a `mailto:` link to `support@ilovefreegle.org` whose body is pre-filled with "Note to support: this freegler was logged in as user id: #<id>" (or "...was not logged in when contacting Support"); this client-appended user id is the only structured identification handed to that channel — [iznik-nuxt3/components/SupportLink.vue](/home/edward/FreegleDockerWSL/iznik-nuxt3/components/SupportLink.vue)
- The AI Support Helper (`ModSupportAIAssistant.vue` + a `claude-agent-sdk/` backend: `server.js`, `support-agent.js`, `prompt.js`, `tools.js`, `auth.js`) is a distinct, currently-live tool for Support/Admin volunteers inside ModTools; it is explicitly a member-investigation copilot, not an automated ticket pipeline — [docs/developers/reference/ai-support-helper.md](/home/edward/FreegleDockerWSL/docs/developers/reference/ai-support-helper.md)
- The AI Support Helper's only outbound "ticket-like" artifact is "Refer to geeks" (`POST /api/refer-to-geeks`): it emails a geeks address with Reply-To the support address, generates a server-side `SR-XXXXX` reference code, requires referral text typed by the volunteer, and the email mirrors the on-screen transcript — [docs/developers/reference/ai-support-helper.md](/home/edward/FreegleDockerWSL/docs/developers/reference/ai-support-helper.md)
- `ModSupportContactGroup.vue` and `ModChatFooter.vue` exist under `iznik-nuxt3/modtools/components/`, but their contents were not opened in this pass — found only via filename search — [iznik-nuxt3/modtools/components/ModSupportContactGroup.vue, ModChatFooter.vue, this session]
- No dedicated `ContactSupportModal`/`HelpChatFlow` components exist; the only files matching those names in a repo-wide grep were `WhichPostsExplanation.vue`, `pages/help.vue`, and `pages/unsubscribe/[[id]].vue`, which appear to be incidental text matches rather than a dedicated support-chat component — [grep results, this session]

### Inferences
- Freegle's support intake is two unconnected systems: an outbound-only email convention (support@, and the "refer to geeks" referral) with no server-side record beyond an email and a reference code, and a stateless, on-demand investigation tool (AI Support Helper) that produces a chat transcript per session but, as far as this pass could confirm, persists no ticket/case object in the database schema.
- Because `SR-XXXXX` codes and the "logged in as user id #N" mailto convention are the only structured identifiers found, there is no way to query "all open support issues" from the database — the record lives in email inboxes and, for AI Support Helper sessions, apparently nowhere durable once the ModTools tab is closed.

### Gaps
- The contents of `ModSupportContactGroup.vue` and `ModChatFooter.vue` were not read — unclear whether either is a genuine ticket/contact mechanism distinct from AI Support Helper or `SupportLink.vue`.
- Whether AI Support Helper chat sessions are persisted anywhere server-side (e.g. a chat-history table) was not directly confirmed against the DB schema; the architecture doc's tool table does not mention one, but this is not conclusive.
- Whether the `ai-flower`/`WorkflowEngine` flowchart redesign proposed for the AI Support Helper (see next question) was actually implemented — this bears directly on whether "admin support tooling" here is structured or free-form today.

## Check plans/ and docs/ for prior ticketing/support-intake designs

### Takeaway
Three related but distinct planning documents exist. None describes or proposes a conventional multi-source ticketing system; instead they document (1) removing an anonymization layer from the AI Support Helper, (2) a proposal — implementation status unconfirmed — to replace its free-form prompt with a constrained FSM of investigation flows after a real confabulation incident, and (3) a still-unbuilt proposal for better diagnostic-info collection from members.

### Cited Findings
- `plans/2026-07-13-ai-support-helper-rebuild.md` documents tearing out a browser-held-JWT design plus `query-sanitizer`/`pseudonymizer`/`mcp-interface` services that used to strip PII before it reached the model, replacing it with direct, non-anonymized read-only access, and a `cli`/`api` driver abstraction selected by an environment variable — [plans/2026-07-13-ai-support-helper-rebuild.md](/home/edward/FreegleDockerWSL/plans/2026-07-13-ai-support-helper-rebuild.md)
- `plans/2026-07-13-support-helper-investigation-flowcharts.md` proposes replacing the AI Support Helper's free-roaming system-prompt agent with a constrained `ai-flower` `WorkflowEngine` FSM of roughly 12 named investigation flows plus a roughly 23-item forced "read-action library," motivated by a real incident where the helper wrongly blamed a member's review flag on a community that had actually already been reviewed and cleared months earlier — [plans/2026-07-13-support-helper-investigation-flowcharts.md](/home/edward/FreegleDockerWSL/plans/2026-07-13-support-helper-investigation-flowcharts.md)
- The same plan validated its proposed flows against 364 real Discourse mod/support reports (drawn from monitor-fsm's own `discourse_bug` table) plus roughly a year of the support mailbox, and found real reports split into three families: member-investigation (a minority, covered by the flows), bug-triage/regression ("still broken after your fix" — the dominant slice, with no flow, falling through to the free-form/confabulation-prone default handling), and product/policy questions (no flow at all) — [plans/2026-07-13-support-helper-investigation-flowcharts.md](/home/edward/FreegleDockerWSL/plans/2026-07-13-support-helper-investigation-flowcharts.md)
- The proposed fix was a 3-way router (`MEMBER_INVESTIGATION` / `BUG_TRIAGE` / `PRODUCT_QUESTION`) plus a new `BUG_TRIAGE` flow ending in a `CAPTURE_FOR_ENGINEERING` terminal state for structured repro capture, explicitly framed in the plan as the structural cure for the confabulation problem — [plans/2026-07-13-support-helper-investigation-flowcharts.md](/home/edward/FreegleDockerWSL/plans/2026-07-13-support-helper-investigation-flowcharts.md)
- `plans/future/help-for-support.md` is an unimplemented proposal (lives under `plans/future/`, Freegle's convention for not-yet-built work) for better diagnostic-info collection from members: Sentry Session Replay in error-only mode, an enhanced device-info composable, an evaluation of third-party tools (Jam.dev, BugHerd, Usersnap, Microsoft Clarity, rrweb), and a proposed new `users_diagnostics` DB table plus Go API endpoints plus a `ModSupportDiagnostics.vue` component — [plans/future/help-for-support.md](/home/edward/FreegleDockerWSL/plans/future/help-for-support.md)
- The current live-system doc (front matter `last_reviewed: 2026-09-23`) still describes the AI Support Helper as driven by "one big system prompt" in `prompt.js` making free-form tool calls, not a constrained flow engine — [docs/developers/reference/ai-support-helper.md](/home/edward/FreegleDockerWSL/docs/developers/reference/ai-support-helper.md)
- A separate diagnosis playbook, built from 115 real escalated `support@` threads (Jan-Jun 2026), defines a decision flow: investigate from the member's data dump first, classify the report as QUESTION vs BUG, and for BUG run commit-aware analysis of roughly the last 14 days reasoning both directions (a commit that fixed it, or one that caused a regression), escalating to a human when nothing matches — [memory: reference_support_ai_diagnosis_playbook, referencing plans/2026-06-15-support-ai-diagnosis-playbook.md]

### Inferences
- Across these documents, Freegle has repeatedly tried to formalize "how should an AI look into a support report," but each iteration reworks the AI's reasoning process (what it may look at, whether it is constrained to named flows) rather than introducing a durable, queryable case/ticket record.
- The flowchart plan's own coverage study is, in effect, a finding that the AI Support Helper structurally under-serves bug-triage and policy-question traffic — which the same document's own count found to be the *majority* of real support volume, not an edge case.

### Gaps
- Whether the `ai-flower`/`WorkflowEngine` redesign proposed in the flowchart plan was actually implemented in `claude-agent-sdk/` was not verified in this pass; the live-system doc's description is consistent with either "never implemented" or "implemented but the doc has gone stale." This is the single most consequential open fact for anyone designing new intake work here, since it determines whether the documented confabulation risk is still live today.
- `plans/2026-06-15-support-ai-diagnosis-playbook.md` itself was not opened directly in this pass (its content here comes via a memory summary); some detail may exist in the file beyond what that summary captured.

## Check .claude/rules/monitor-fsm.md and named memory files for stated lessons/preferences

### Takeaway
The rules file documents that monitor-fsm is failure-silent by default (it looks idle when broken, in several distinct enumerated ways), and the memory files record specific product decisions about when it may post publicly, plus a house-style rule that any volunteer- or member-facing text from these systems must be short and free of implementation jargon.

### Cited Findings
- The driver exits cleanly on several fatal conditions, so "nothing happened" looks identical to "nothing needed doing"; enumerated causes: an out-of-credit API key, a "Prompt is too long" response on the first brain call of a lap being treated as though it were a real answer, a state file truncated to zero bytes killing every run at startup, and a Discourse 429 whose wait-time is in the response body rather than the `Retry-After` header — a caller reading only the header gives up while Discourse is still refusing, and the lap silently continues with no topics or reporter confirmations — [.claude/rules/monitor-fsm.md](/home/edward/FreegleDockerWSL/.claude/rules/monitor-fsm.md)
- `PARSE_ONLY` does not halt at the work router — tool nodes continue into dispatching fixes; confirm behaviour from the run log, not the flag — [.claude/rules/monitor-fsm.md](/home/edward/FreegleDockerWSL/.claude/rules/monitor-fsm.md)
- The fix step and verify step can lap without draining results still in flight, so work is re-decided while its own outcome is still arriving; it also opens PRs and runs its own adversarial review, and leaves a PR open when that self-review fails — an open PR from it is not a reviewed one — [.claude/rules/monitor-fsm.md](/home/edward/FreegleDockerWSL/.claude/rules/monitor-fsm.md)
- Delegate briefs hard-code the main checkout path, so a delegate spawned from a worktree run writes into the main checkout rather than the worktree, unless its working directory is passed explicitly — [.claude/rules/monitor-fsm.md](/home/edward/FreegleDockerWSL/.claude/rules/monitor-fsm.md)
- Edward, 2026-09-19: monitor-fsm has two permitted outbound Discourse post kinds, not one — the verbatim "possible fix applied, please retest" once a fix is live, and a question asking the reporter what a report is missing (which member, group, post, screenshot); a clarifying question that only sits queued for approval and is never sent leaves the report stuck unactionable — [memory: feedback_fsm_may_post_to_clarify]
- The clarifying-question path runs from `persist_classifications` and `ask_reporter_for_detail`, one per reporting post, recorded as posted so the same person is not asked again each lap; a failed post retries. Answers to a moderator's question, by contrast, still wait for dashboard approval, since an answer asserts how Freegle works and a wrong one is worse than a slow one — [memory: feedback_fsm_may_post_to_clarify]
- Volunteer/member-facing replies (Discourse and similar) must be short — state the fix and stop — and must be plain English (no key/class/file names, no coined hyphen-compounds); this is enforced by a hook that scores prose and blocks on failure, run at stricter thresholds for Discourse than for PR descriptions — [memory: feedback_keep_discourse_replies_short]
- Design principle recorded 2026-09-19: humans should add value, but every flow must reach an outcome with zero humans in the loop; a flow gated on a human touch point (a report that waits for a moderator, a message hidden until reviewed) fails the moment that person is not there — [memory: feedback_humans_add_value_system_works_without]
- The support-mailbox research corpus was read via read-only access to a personal mailbox (not the shared support address itself), and used to build the diagnosis playbook from roughly 115 escalated threads — [memory: reference_support_mailbox_imap_access]

### Inferences
- The rules file's enumerated "looks idle when broken" failure modes are a strong, concrete argument that any new multi-source intake design should carry a positive liveness signal (e.g. a last-successful-lap timestamp) rather than relying on the absence of errors as evidence of health.
- The house policy visible across these memories — an AI may autonomously ask the reporter for missing facts, but any output asserting how the product behaves needs human approval — reads as a general principle, not one specific to monitor-fsm, and would likely apply to any new intake system built the same way.

### Gaps
- None of substance for this question; the rules file and the five named memory files were all read in full for this pass.

## How does the system identify the affected member? How does it gauge urgency? How does it dedupe reports?

### Takeaway
Identification, urgency, and dedup are handled completely differently — and mostly informally — across the two systems: monitor-fsm never resolves a report to a member at all (it works only from Discourse usernames and Sentry issue ids), the AI Support Helper requires an explicit member-resolution step up front but, per the flowchart plan's own coverage study, that only fits a minority of real report types; neither system has a formal urgency/severity score, and dedup in both is manual/heuristic rather than automated.

### Cited Findings
- `discourse_bug`'s primary key is `(topic, post)`; `reporter` is stored as a free-text Discourse username, not a resolved member id — there is no join anywhere in the `monitor.db` schema to Freegle's member table — [monitor-fsm/monitor.db schema, this session](/home/edward/FreegleDockerWSL/monitor-fsm/monitor.db)
- `sentry_issue` is keyed on `issue_id` with no user/member reference in its schema at all — [monitor-fsm/monitor.db schema, this session](/home/edward/FreegleDockerWSL/monitor-fsm/monitor.db)
- Neither `discourse_bug` nor `sentry_issue` has an urgency/severity/priority column; the closest analogues are `pr_rejections` (a retry counter) and the state/disposition enums themselves, which encode report type and progress, not severity — [monitor-fsm/monitor.db schema, this session](/home/edward/FreegleDockerWSL/monitor-fsm/monitor.db)
- The AI Support Helper documents `identify_user` (resolve email/name/id to a member) as a tool that "must be done first," followed by `get_user_dump`/`query_dump`, which streams a self-contained per-member SQLite dump of roughly 69 tables plus a three-pass Loki log query plus Sentry issues (secrets redacted), over a 90-day window by default — [docs/developers/reference/ai-support-helper.md](/home/edward/FreegleDockerWSL/docs/developers/reference/ai-support-helper.md)
- The support diagnosis playbook (115 real escalated threads) records the closest thing to a triage/urgency heuristic found: investigate from the member's data dump first, classify QUESTION vs BUG, and for BUG run commit-aware analysis of roughly the last 14 days checking both directions (a commit that fixed it, or one that caused a regression), escalating to a human when nothing matches — this is a routing decision (who/what handles it next), not a numeric urgency score — [memory: reference_support_ai_diagnosis_playbook]
- The same playbook explicitly warns that matching a symptom's date to a commit's date does not prove the bug pre-existed the report: a later re-check found essentially all of its own earlier "known bug, already fixed" matches were actually reactive — the commit was written *in response to* that very report — so commit-matching is only safe for "has a fix already shipped since," never as prior knowledge — [memory: reference_support_ai_diagnosis_playbook]
- monitor-fsm's own dedup-relevant rules (from a 2026-05-31 sweep) are heuristic and were derived after the fact from real mistakes, not from a live automated mechanism: "collapse me-too confirmations under the primary report" and "consolidate duplicate-topic bugs before fixing" (two separate Discourse topics describing the same chat-filter regression) were both findings about what the FSM had failed to do, not descriptions of a working dedup feature — [monitor-fsm/SWEEP-FINDINGS-2026-05-31.md](/home/edward/FreegleDockerWSL/monitor-fsm/SWEEP-FINDINGS-2026-05-31.md)
- `discourse_bug.state` does include a literal `duplicate` value, so the FSM can classify a report as a duplicate, but this is a triage classification made by the triage/brain call, not a computed similarity or fuzzy-match algorithm — [monitor-fsm/monitor.db schema, this session](/home/edward/FreegleDockerWSL/monitor-fsm/monitor.db)
- The flowchart plan's coverage study (364 real Discourse reports plus roughly a year of the support mailbox) found the AI Support Helper's identify-first design serves only the "member investigation" family, which was itself a minority of real traffic; the dominant "bug triage/regression" family and a further "product/policy question" family are not member-identification problems at all and have no structured path — [plans/2026-07-13-support-helper-investigation-flowcharts.md](/home/edward/FreegleDockerWSL/plans/2026-07-13-support-helper-investigation-flowcharts.md)
- The public `support@` mailbox's only member-identification aid is the client-appended "logged in as user id #N" line from `SupportLink.vue`'s mailto body — there is no server-side resolution step for that channel; a human reading the email must act on that line manually — [iznik-nuxt3/components/SupportLink.vue](/home/edward/FreegleDockerWSL/iznik-nuxt3/components/SupportLink.vue)

### Inferences
- There is no unified urgency/severity concept anywhere in this machinery: monitor-fsm effectively encodes "how fast" as a function of category and a hard-coded escalation threshold (rejections before human hand-off) rather than a stored severity value, and the AI Support Helper has no severity concept at all — it is a per-session investigation tool, not a prioritized queue.
- Dedup in both systems is post-hoc and heuristic: monitor-fsm's dedup rules exist *because* a retrospective sweep found it had failed to deduplicate two topics about the same regression, not because a working similarity check exists; no embedding-based or fuzzy-match dedup was found anywhere in the schema or documentation reviewed.
- Because `identify_user` is mandatory and unconditional at the start of every AI Support Helper session, a report that is not about one identifiable member (a general bug, a policy question) structurally has no home in that tool — consistent with the flowchart plan's finding that non-member-investigation traffic is the dominant, unserved slice.

### Gaps
- Whether monitor-fsm ever resolves a Discourse username to an internal member id during diagnosis (rather than only storing the free-text username) was not directly confirmed against the diagnosis/fix workflow code — only the SQLite schema, which stores no such id, was inspected in this pass.
- Whether Sentry issues are ever cross-referenced to a member id at runtime (Sentry payloads typically carry a user context) was not checked; the `sentry_issue` table itself carries none, but the raw Sentry ingestion code was not inspected.

## Where has the system fallen short (concrete weaknesses)?

### Takeaway
There is a well-documented, dated, first-party record of monitor-fsm giving up on real bugs — marking them fixed, dismissed, or deferred when they were not — and a separately documented, more structural finding that the AI Support Helper's investigation coverage misses the majority of real support traffic; both come from dedicated retrospective audits rather than external critique, and in both cases the fixes proposed are only partially implemented.

### Cited Findings
- A dedicated human/AI sweep (`monitor-fsm/SWEEP-FINDINGS-2026-05-31.md`) reviewed FSM verdicts against real Discourse threads and found at least 9 genuinely still-broken bugs the FSM had wrongly marked fixed, dismissed, or deferred — including one deferred despite the admin publicly acknowledging the bug in the same thread, and one where a PR over-filtered a query (excluding pending messages that should have stayed included) and was marked fixed off an early "fix worked" post while a later contradicting post 4 days on was ignored — [monitor-fsm/SWEEP-FINDINGS-2026-05-31.md](/home/edward/FreegleDockerWSL/monitor-fsm/SWEEP-FINDINGS-2026-05-31.md)
- The same sweep found a data-integrity bug in the FSM itself: it created a verdict record referencing post 22 of a Discourse topic that has only 21 posts — a phantom post — because it never validated the post existed before persisting a verdict — [monitor-fsm/SWEEP-FINDINGS-2026-05-31.md](/home/edward/FreegleDockerWSL/monitor-fsm/SWEEP-FINDINGS-2026-05-31.md)
- The sweep's resulting rule list (9 rules) includes: never mark fixed while a reporter says still-broken; require fix evidence (a linked PR or reporter confirmation) before fixed/off-topic, rather than treating silence as confirmation; don't link a PR to a report by timeline proximity alone — verify the diff touches the reported symptom; treat a changed symptom description as a new bug rather than re-blaming the same prior PR; collapse "me too" replies under the primary report; let an admin's public acknowledgement block deferral; validate a cited post actually exists; treat one rejected PR as a signal to re-diagnose, not an immediate hand-off to a human; and consolidate reports of the same bug filed as separate topics — [monitor-fsm/SWEEP-FINDINGS-2026-05-31.md](/home/edward/FreegleDockerWSL/monitor-fsm/SWEEP-FINDINGS-2026-05-31.md)
- Of those 9 rules, the sweep's own status tracking records only 2 as shipped as deterministic code (a "still broken" guard, and raising the escalation threshold from 1 rejected PR to 2); the rest are recorded as "prompt-level guidance ... not deterministic" — i.e. advisory to the triage LLM rather than enforced in code — [monitor-fsm/SWEEP-FINDINGS-2026-05-31.md](/home/edward/FreegleDockerWSL/monitor-fsm/SWEEP-FINDINGS-2026-05-31.md)
- Separately, the AI Support Helper had a real documented confabulation incident: it wrongly blamed a member's review flag on a specific community when that flag had actually already been reviewed and cleared months earlier — this directly motivated the 2026-07-13 flowchart redesign proposal — [plans/2026-07-13-support-helper-investigation-flowcharts.md](/home/edward/FreegleDockerWSL/plans/2026-07-13-support-helper-investigation-flowcharts.md)
- That plan's coverage-validation exercise (364 real Discourse reports plus roughly a year of the support mailbox) found the investigation flows serve only a minority of real traffic; the dominant category ("still broken after your fix" bug-triage/regression reports) and a further slice (product/policy questions) have no structured flow and fall into free-form, confabulation-prone default handling — [plans/2026-07-13-support-helper-investigation-flowcharts.md](/home/edward/FreegleDockerWSL/plans/2026-07-13-support-helper-investigation-flowcharts.md)
- `.claude/rules/monitor-fsm.md` separately records that the driver fails silently under at least 4 distinct conditions (out-of-credit key, an unhandled "prompt too long" response, a truncated state file, a mis-parsed Discourse 429), so an operator cannot tell "the queue is genuinely empty" from "the loop is broken" without extra checks — [.claude/rules/monitor-fsm.md](/home/edward/FreegleDockerWSL/.claude/rules/monitor-fsm.md)
- The rules file also records that opening a PR is not the same as having it reviewed: the FSM runs its own adversarial review and leaves a PR open even when that self-review fails — [.claude/rules/monitor-fsm.md](/home/edward/FreegleDockerWSL/.claude/rules/monitor-fsm.md)

### Inferences
- The two systems fail in structurally similar ways despite being architecturally separate: both were found, by dedicated retrospective audits, to give up too early on genuinely unresolved reports rather than failing loudly — monitor-fsm by wrongly marking bugs fixed/dismissed, the AI Support Helper by having flows that cover only a minority of report types.
- The gap between "9 rules identified" and "2 shipped as deterministic code" in the sweep findings suggests monitor-fsm's real-world reliability today likely still sits closer to the pre-sweep baseline than the full fix list implies, since 7 of the 9 fixes rely on prompt guidance rather than enforced logic.

### Gaps
- No verification was done of whether the 7 prompt-level (non-deterministic) sweep rules have since been folded into `workflow.json`'s actual prompts, or remain purely documented intent.
- Whether a similar retrospective sweep has been run more recently than 2026-05-31 (i.e. whether these are still live failure modes, or have since been re-audited and improved) was not checked in this pass.
