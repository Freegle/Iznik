# Established Operating Models and Data Models for Multi-Channel Customer Support

## Omnichannel data model: contact/person, identity resolution, conversation vs ticket vs case, message/part, channel adapters, threading, attachments

### Takeaway
The three market-leading object models (Zendesk, Intercom, Chatwoot) converge on the same shape: a **person/contact** entity that is channel-agnostic, a **conversation/ticket** entity that is channel-specific and belongs to one inbox, and a **message/part** entity that represents one turn within the thread — with a separate join entity handling the many-to-many between a person and the channel-specific identifiers (email address, forum account id, app account id, chat widget session) that let a reply be re-attached to the right thread. Email-specific threading is solved with standard RFC headers (Message-ID / In-Reply-To / References) plus a vendor-added fallback token embedded in outbound notification emails, because header-based threading alone is fragile (dropped headers, forwarding, thread age limits).

### Cited Findings
- **Zendesk**: the core object is the **Ticket**; there is a separate **Requests API** giving the end user's restricted view of the same object, while the **Tickets API** is the agent/admin view — "a ticket is the agent's view of a ticket, and a request is the end user's view of it." Every ticket has a `requester` and a `submitter`, and a `via` object records how/why it was created (channel, from/to/rel of the source). Changes are recorded in an **Audit** object with an `events` array. — [Zendesk Tickets API](https://developer.zendesk.com/api-reference/ticketing/tickets/tickets/), [Via object reference](https://developer.zendesk.com/documentation/ticketing/reference-guides/via-object-reference/)
- Zendesk's **Ticket Metrics** object separately tracks timestamps used for reporting (`agent_wait_time_in_minutes`, `assigned_at`, `assignee_updated_at`, etc.), i.e. metrics are modelled as their own object rather than fields bolted onto the ticket. — [Ticket Metrics](https://developer.zendesk.com/api-reference/ticketing/tickets/ticket_metrics/)
- **Intercom**: the core object is the **Conversation**, created either by a contact replying to an outbound message or an admin messaging a contact directly. A conversation holds `contacts`, `teammates`, `assignee`, `open`/`state`/`read`/`waiting_since`/`snoozed_until`, `tags`, and a `source` object (author, body, `delivered_as`, e.g. "customer_initiated"). Each turn in the thread is a separate **Conversation Part** object (`part_type`, `body`, `author`, `attachments`, timestamps) — messages are not embedded as plain strings on the conversation, they are first-class sub-objects, capped at 500 returned parts per conversation. — [Intercom conversation model](https://developers.intercom.com/docs/references/2.4/rest-api/conversations/conversation-model), [Conversation Part model](https://developers.intercom.com/docs/references/1.4/rest-api/conversations/conversation-part-model)
- Intercom conversations carry a **Statistics** object purpose-built for reporting, an **SLA** object, a **Conversation Rating** object (CSAT), and "linked objects" metadata connecting a conversation to up to 1,000 other conversations/tickets — an explicit merge/relate mechanism rather than assuming 1:1. Newer versions add fields for whether an AI agent participated and which channel the conversation started on vs. is currently on (channel can change mid-thread). — [Retrieve a conversation, v2.16](https://developers.intercom.com/docs/references/rest-api/api.intercom.io/conversations/retrieveconversation)
- **Chatwoot**'s model is explicit about the identity-resolution join: **Account → Contact → ContactInbox → Inbox(Channel) → Conversation → Message**. `ContactInbox` is "the join model" that "ties a Contact & Inbox using the appropriate `source_id`" — the source_id is the channel-specific identifier (webwidget session hash, Twitter id, WhatsApp phone number, email address). "The contact model groups conversations from different inboxes that belong to the same person," i.e. one Contact can have many ContactInboxes across channels, and this is the mechanism that answers "is this the same person who emailed us and posted on the forum?" — [Chatwoot core data models (DeepWiki)](https://deepwiki.com/chatwoot/chatwoot/3-core-data-models), [Contact management (DeepWiki)](https://deepwiki.com/chatwoot/chatwoot/3.3-conversation-and-message-models)
- Chatwoot's **Inbox** is a container wrapping a polymorphic **Channel** (`channel_email`, `channel_whatsapp`, etc.) — "This pattern allows new channels to be added without modifying the core conversation or message logic," i.e. the channel-adapter pattern is implemented as polymorphic association, not a big if/else on channel type. Conversations get four statuses: Open, Pending, Snoozed, Resolved, and a resolved conversation is never deleted — full history stays attached to the contact. — [Inboxes and Channels (DeepWiki)](https://deepwiki.com/chatwoot/chatwoot/3.5-inboxes-and-channels)
- **Plain** (API-first B2B support tool) models everything — "customers, threads, timeline entries, messages, labels, tiers, and webhooks" — through one GraphQL API. Its **Thread** is the unit of support work (create/fetch/update/assign/escalate/change status), and a **Timeline** "unifies messages, status changes, label changes, and your own structured events into one feed" per thread — an explicit event-sourced/activity-stream design rather than a flat message list. Threads carry a priority enum: `urgent > high > normal (default) > low`. Customer upsert is idempotent, keyed on external id or email (`onCreate`/`onUpdate` semantics), which is itself a documented identity-resolution primitive. — [Plain API-first support](https://www.plain.com/blog/what-is-api-first-customer-support), [Plain-support API profile](https://github.com/api-evangelist/plain-support)
- **Email threading mechanics**: every email gets a globally unique `Message-ID`; a reply's `In-Reply-To` header points to the Message-ID it answers; `References` lists every Message-ID in the thread oldest-to-newest so the full tree can be rebuilt even if intermediate replies are missing. — [Threading: Message-ID, References, In-Reply-To](https://cr.yp.to/immhf/thread.html)
- Zendesk's practical implementation: it "compares the message IDs in the References and In-Reply-To lines against existing tickets" to thread a reply, and as a fallback "every outgoing notification email includes an encoded ID by default to help match replies to the right ticket" (a reply token). Known failure modes: header matching only works for 30 days after the original email; if headers are missing/stripped a new ticket is opened instead of threading; a fixed/duplicated Message-ID on outbound mail can cause unrelated replies to merge into the same ticket. — [How incoming emails thread to tickets](https://support.zendesk.com/hc/en-us/articles/8396827889946-How-are-incoming-emails-threaded-to-tickets), [Why emails thread to the wrong ticket](https://support.zendesk.com/hc/en-us/articles/4408821051034-Why-do-emails-thread-to-the-wrong-ticket)
- BoldDesk and Nylas describe the same reply-token pattern for custom-built ticketing: store the outbound `Message-ID`/thread id alongside your own ticket record; when a reply arrives, look up by that id; a match means "reply to something you sent," no match means "new conversation to triage." For backward compatibility, readers should fold `In-Reply-To` into `References` if a client sent one without the other. — [BoldDesk automatic email threading](https://support.bolddesk.com/kb/article/12831/automatic-email-threading-how-it-works), [Nylas email threading for agents](https://developer.nylas.com/docs/v3/agent-accounts/email-threading/)

### Inferences
- The recurring pattern across all four vendors is a **4-layer model**: Person (channel-agnostic) → Person-Channel-Identity join (channel-specific id/source_id) → Conversation/Thread/Ticket (belongs to one channel/inbox) → Message/Part (one per turn, itself sometimes carrying its own sub-events like status/label changes). A bespoke Freegle design should keep these as four distinct concepts even if some are collapsed into one DB table initially, because the join layer (Chatwoot's `ContactInbox`, analogous to matching an email address, Discourse account, and app account to one person) is precisely the piece needed to answer "has this member/moderator reported this before, on a different channel?" — the identity-resolution question the brief asks about.
- None of the vendor docs found describe a general-purpose fuzzy identity-resolution algorithm (matching by name/IP/device fingerprint) — all of them require an explicit identifier per channel (email address, external id, source_id) supplied at creation/upsert time. This implies identity resolution across email/forum/app accounts for Freegle will likely need to be **explicit** (e.g., matching on verified email address) rather than probabilistic, unless a separate step is added.
- The email reply-token pattern (encode a matchable id in the outbound notification, independent of RFC headers) is the more robust design than relying on `In-Reply-To`/`References` alone, since Freegle's real-world mail will pass through Yahoo/Gmail/Outlook clients whose header handling cannot be controlled (compare `finding_yahoo_family_delivery_collapsed_2026_08_16` — mail-related fragility with major providers is already a known risk area in this codebase's own history).

### Gaps
- Did not find vendor documentation for **Zendesk's or Intercom's contact-merge algorithm** specifically (e.g., what happens when two Contacts are later found to be the same person) beyond Intercom's "linked objects" (which links conversations/tickets, not necessarily merges people). This would need a follow-up search on "Zendesk merge users" / "Intercom merge contacts" if the design needs a dedup/merge workflow.
- Did not find a full field-by-field schema for Plain's `Thread` and `Customer` GraphQL types (paywalled/requires API key to introspect); only the conceptual shape was available from secondary sources.
- Attachment modelling specifics (size limits, virus scanning, how an attachment is associated with a message vs. a conversation) were not directly researched — out of scope given the 15-tool-call budget; flagged as a gap for a follow-up pass if attachment handling design detail is needed.

## ITIL 4 / service management: incident vs problem vs known error vs service request vs change; priority = impact × urgency; major incident handling; KCS

### Takeaway
ITIL 4 gives four cleanly distinguishable categories — **incident** (unplanned break/degradation), **problem** (the cause, or potential cause, of one or more incidents), **known error** (a problem that has been analysed but not yet resolved), and **service request** (a pre-agreed, routine ask, not something broken) — prioritised by an impact×urgency matrix that typically yields 3–5 priority tiers, with a distinct escalation path ("Major Incident Management") once impact and urgency are both high. KCS adds a complementary practice: knowledge articles are written as a byproduct of resolving issues, not as separate documentation work, which is the ITIL-adjacent practice most directly reusable at small scale.

### Cited Findings
- ITIL 4 definitions: **Incident** = "an unplanned interruption to a service, or reduction in the quality of a service" (ITIL 4 dropped "IT" from the ITIL v3 wording, generalising the term beyond IT services). An incident can be raised even before an SLA is breached, "in order to limit or prevent impact." — [Global Knowledge: How ITIL differentiates problems and incidents](https://www.globalknowledge.com/us-en/resources/resource-library/articles/how-itil-differentiates-problems-and-incidents/)
- **Problem** = "a cause, or potential cause, of one or more incidents." Problem management has three phases: **Problem identification, Problem control, Error control**. — [Atlassian: Problem Management in ITIL](https://www.atlassian.com/itsm/problem-management)
- **Known error** (ITIL 4) = "a problem that has been analysed and has not been resolved" — broader than the older/common wording ("a problem with a documented root cause and workaround"). Known errors may be tracked in a **Known Error Database (KEDB)** recording root cause, workaround, and fix status; a known error stays in that state "until a permanent fix is implemented or the affected system is decommissioned." — [Known error, Wikipedia](https://en.wikipedia.org/wiki/Known_error)
- **Service request** (ITIL 4) = "a request from a user or user's authorized representative that initiates a service action that has been agreed as a normal part of service delivery." Typical sub-types: an action request, an information request, an access request, and "feedback, compliments, or complaints." — [ManageEngine: ITIL service request vs incident](https://www.manageengine.com/products/service-desk/itsm/service-request-management.html)
- **Distinguishing incident from service request in practice**, two questions: (1) "was it working before? If yes, and it is not now, it is an incident." (2) "is there an existing, approved procedure for delivering this? If yes, and nothing is broken, it is a request." Historically these were not distinguished at all until ITIL v3 (2007) lumped both under "incidents" before splitting them. — [itil.org.uk: Incident vs Service Request](https://www.itil.org.uk/blog/incident-vs-service-request)
- **Priority matrix**: standard model is a 3×3 grid (three levels each of impact and urgency) producing five priority levels P1 (critical) to P5 (lowest); some organisations use only 4 levels, others (e.g. TOPdesk) use 3 urgency levels × their own impact scale to get 7 priority levels. "No matrix is a one-size-fits-all... labels can stay the same, but what each one means can differ between organisations." Impact is judged by "how many users are impacted, whether a critical business service is unavailable, and if there is any risk to revenue, regulatory compliance, or organizational reputation"; urgency is "how quickly a resolution... is required." PagerDuty: impact and urgency are treated as **equally important** in setting priority. — [InvGate: ITIL priority matrix](https://blog.invgate.com/itil-priority-matrix), [PagerDuty: Incident priority matrix](https://www.pagerduty.com/resources/digital-operations/learn/incident-priority-matrix/)
- **Major Incident Management (MIM)** is "a sub-process of Incident Management," not a separate ITIL practice — "a specialized procedure... for emergencies that affect business-critical services and require immediate attention." A major incident is defined not necessarily by technical complexity but by business harm: "a major incident is not necessarily the most technically complex — it's the one that hurts the business the most." High-impact × high-urgency in the priority matrix triggers the full MIM workflow. — [Cutover: What is major incident management](https://cutover.com/blog/what-is-major-incident-management-why-your-business-cant-ignore-it), [Alloy Software: Major Incidents in ITIL 4](https://www.alloysoftware.com/blog/major-incident-management-itil-4/)
- MIM process steps (Ivanti): **logging → categorisation → escalation → formation of a temporary Major Incident Team → workaround/restoration**, with root-cause analysis deferred — "restoring service quickly before doing root cause analysis." Key roles: a **Major Incident Manager** (accountable for driving the process and keeping stakeholders informed of progress), a **Problem Manager** (root-cause work — Advisera notes this role "can't be combined with the incident management role, due to the well-known conflict of interests" between racing to restore service vs. taking time to find the cause), and a **Change Manager** (if an urgent change is needed to restore service). — [Ivanti: ITIL major incident roles](https://www.ivanti.com/blog/what-are-the-primary-itil-major-incident-management-roles-and-responsibilities), [Advisera: Major incident management](https://advisera.com/20000academy/knowledgebase/major-incident-management-going-gets-tough/)
- Each organisation sets its own "major" threshold; Atlassian's own incident model uses three severities where the top two (SEV1, SEV2) both count as "major." — [Cutover](https://cutover.com/blog/what-is-major-incident-management-why-your-business-cant-ignore-it)
- **KCS** (Knowledge-Centered Service, formerly Knowledge-Centered Support) was developed from 1992 by the **Consortium for Service Innovation**, a non-profit of service organisations. Core tenet: "KCS is not something we do in addition to solving problems. KCS is the way we solve problems" — knowledge articles are created/refined as a byproduct of resolving real issues, not as separate documentation work. Every issue is triaged as "known" (point the person at existing content) or "new" (solve it, then capture it). Ownership of the knowledge base is collective — "all support agents [are] responsible for adding and refining articles" — rather than resting with dedicated knowledge managers/writers. A licensing model exists to control who may edit public-facing articles. — [Wikipedia: Knowledge-centered support](https://en.wikipedia.org/wiki/Knowledge-centered_support), [Consortium for Service Innovation: KCS](https://www.serviceinnovation.org/kcs/)
- Cited benefits of KCS: faster fixes (agents reuse peer-written articles instead of re-researching), lower cost via self-service/fewer escalations, more consistent answers, faster onboarding of new staff, and a clearer view of recurring problems (frequent searches/usage surface content gaps). In 2026 the Consortium rebranded it "Knowledge-Centered **Success**" and is positioning it explicitly as a prerequisite for AI/agentic support tooling, arguing "validated, demand-driven data prevents hallucinations and builds user trust." — [Consortium for Service Innovation](https://www.serviceinnovation.org/kcs/)

### Inferences
- For a "tiny dev team" the full ITIL taxonomy is more than needed, but the **incident/problem/known-error split** is the one piece worth keeping distinct even at small scale, because it separates three different lifecycles that otherwise get conflated in a single "bug ticket": (a) the live symptom a member is experiencing right now (incident-equivalent — needs a fast, possibly temporary fix/workaround), (b) the underlying code defect (problem-equivalent — needs a PR), and (c) the fact that the defect is known-but-not-yet-fixed (known-error-equivalent — needs to be visible to whoever answers the *next* report of the same symptom, which is exactly Freegle's Discourse-forum-plus-Sentry-plus-email situation: several people can hit the same bug through different channels before a fix ships).
- The **service request vs incident** two-question test ("was it working before?" / "is there a pre-agreed procedure?") is a cheap, low-ceremony heuristic a small team can apply without building a full ITSM tool, and maps directly onto Freegle's existing traffic: "my post isn't showing" (incident) vs. "please delete my account" (service request with a pre-agreed procedure, and per findings below, also a possible GDPR erasure request).
- Full **Major Incident Management** ceremony (temporary MIM team, dedicated Major Incident Manager role, formal stakeholder comms cadence) is very likely overkill for Freegle's normal volume, but the *underlying principle* — restore/mitigate first, defer root-cause analysis, and treat "impact on many members" as the trigger rather than technical severity — is directly reusable for, e.g., a mail-delivery outage affecting many groups at once (cf. this codebase's own Yahoo-mail-collapse finding, which was exactly a high-impact, ongoing incident that arrived piecemeal via multiple channels before its scope was understood).
- KCS is the highest-leverage, lowest-overhead practice in this list for Freegle's structure specifically: a small paid dev team plus many volunteer moderators is structurally similar to KCS's "collective ownership by frontline agents" model, and Freegle already has a natural knowledge-base candidate in its own `docs/` tree and Discourse categories — the missing piece per KCS is treating *every resolved report* as an opportunity to write/update a doc, not treating documentation as separate follow-up work.

### Gaps
- Did not find a citable ITIL source specifically discussing how these practices scale down for very small/volunteer-heavy organisations (all sources found are enterprise-ITSM-vendor-oriented). This is inference, not a cited finding, and should be flagged as such to the report writer.
- Did not verify whether KCS's Consortium publishes a specific "KCS for small/nonprofit teams" guide; only the general Practices Guide and Adoption Guide were identified by title, not fetched.

## Priority/urgency heuristics used in practice; swarming vs tiered support

### Takeaway
Impact and urgency remain the two inputs practitioners actually use to set priority (impact = breadth/severity of harm — safety, money, number of people, reputation/regulatory risk; urgency = time sensitivity), but for small teams the more consequential design choice is **support delivery model**: tiered (queue-and-escalate, good for high-volume/repetitive work) versus swarming (whoever picks it up keeps it and pulls in help in real time, good for lower-volume/complex work, and specifically recommended by multiple sources for smaller teams).

### Cited Findings
- Impact is assessed by "how many users are impacted, whether a critical business service is unavailable, and if there is any risk to revenue, regulatory compliance, or organizational reputation"; urgency is "how quickly a resolution... is required," and the two are weighted as **equally important** by PagerDuty's guidance. — [InvGate](https://blog.invgate.com/itil-priority-matrix), [PagerDuty](https://www.pagerduty.com/resources/digital-operations/learn/incident-priority-matrix/)
- "Without a defined matrix, prioritization often depends on whoever picks up the ticket first. Over time, inconsistent prioritization affects SLAs, increases backlog volume, and creates friction between support teams and the business." — [InvGate](https://blog.invgate.com/itil-priority-matrix)
- **Tiered support**: Tier 1 = generalist frontline (password resets, basic how-tos); Tier 2 = deeper product knowledge; Tier 3 = the engineers/specialists who built the product; ownership changes hands at each escalation. Criticisms: tickets can "bounce" between teams multiple times; the model is "fundamentally siloed," reducing "opportunities for knowledge dissemination"; queues form because "a single issue may wait in a number of teams' ticket queues, each adding a delay"; and "a system of tiered support naturally puts the most skilled support at the back," so "the route to the person best placed to resolve an issue is often blocked." — [Helply: Swarming vs. tiered support](https://helply.com/blog/swarming-vs-tiered-support)
- **Swarming**: "the agent who opens a case keeps it and recruits help instead of handing it off." BeyondTrust: swarming favours "real-time work over queued work, collaboration over silos, and case ownership over one-way escalations." HDI: swarming "can deliver faster and more effective response and resolution" for some organisations, and lets first-tier staff "watch and learn from subject matter experts... during remote support sessions, improving on-the-job training and employee retention." — [BeyondTrust](https://www.beyondtrust.com/blog/entry/what-is-the-it-support-swarming-model), [HDI: Evaluating Technical Support Models](https://www.thinkhdi.com/library/supportworld/2017/evaluating-technical-support-models-tiered-support-vs-swarming-part-2)
- Swarming's drawbacks: requires "a lot of rearranging of processes and expectations"; without preparation "the strategy can be relatively unstructured and disorganized"; Freshworks notes adopters cite "teams' resistance to change, steep learning cycles, the non-availability of set models to replicate," and that swarming "has found greater success in organizations adopting DevOps than those that haven't." — [Freshworks: Swarming vs tiered](https://www.freshworks.com/explore-it/three-tier-support-vs-swarming/)
- On team size, sources are split but lean toward swarming for small teams: Help Scout says swarming "is excellent for smaller companies or groups that can move with agility," while it's "pretty challenging for big companies... unless you create smaller groups." Helply similarly says "tiered fits larger teams with predictable, repetitive queues." (Freshworks is an outlier, suggesting tiered support "can suit teams whose team size is small" if the work is uniform.) Giva frames it as not mutually exclusive: "For simple issues, the support team can use a Tiered Support approach, whereas, for more complex issues, the support team can initiate a swarm." — [Help Scout: Swarming vs. Tiering](https://www.helpscout.com/blog/support-team-swarming-vs-tiering/), [Giva: Intelligent Swarming](https://www.givainc.com/blog/what-is-swarming-it-customer-support-teams/)
- The general rule of thumb across sources: "swarming wins on complex, lower-volume queues and tiered wins on high-volume, repetitive ones." — [Helply](https://helply.com/blog/swarming-vs-tiered-support)

### Inferences
- Freegle's actual shape — a tiny paid dev team, many volunteer moderators, and low-to-moderate report volume per channel — matches the profile multiple sources associate with swarming rather than tiered support: complex/varied reports (not a call-centre volume of repetitive password resets), and a team small enough that "recruit help in real time" is operationally simpler than standing up formal tiers with handoff overhead. This suggests the moderators-as-Tier-1/dev-team-as-Tier-2/3 framing that might seem natural to borrow from ITIL is *not* the best fit; a lighter model where a moderator who spots something pulls in a developer directly (or escalates into a shared queue everyone watches) fits the sources' size guidance better.
- No single source gives a ready-made impact/urgency rubric specific to a volunteer-run reuse charity; the report should treat "impact" and "urgency" as reusable *categories* but expects the actual scoring rules (e.g., what counts as high impact for Freegle) to be designed bespoke, informed by the safeguarding/GDPR considerations in the next section.

### Gaps
- Did not find a citable source specifically measuring sentiment as a triage input (the brief asks about "sentiment" as a heuristic) — this appeared implicitly in vendor CSAT/NPS material but not as a documented triage rule; flagged as a gap.
- Did not find published "triage SLA" benchmarks specific to small/volunteer teams (all SLA discussion found was enterprise-oriented, e.g. PagerDuty/InvGate). The First-Response-Time findings below give general benchmarks but not small-team-specific ones.

## Special considerations: volunteer/moderator reporters vs end-user members; proxy reporting; escalation; safeguarding/abuse bypassing AI; GDPR SAR/erasure via support

### Takeaway
UK GDPR requires that **any** channel and **any** wording can constitute a valid Subject Access Request or erasure request — including tickets arriving through a support inbox — so intake design must treat "is this a data-rights request?" as a check applied to all incoming messages, not a separate form; on the safeguarding/trust-and-safety side, the emerging consensus across sources is a hybrid model where automation handles clear-cut, low-risk cases and always escalates ambiguous, high-risk, or safety-relevant reports to a human, with named escalation ownership and reversible/audited actions.

### Cited Findings
- **Any wording, any channel counts as a SAR**: "A person doesn't need to say 'subject access request,' mention any law or fill in a form. If someone asks 'what information do you hold about me?' or 'please send me all my data,' that's a valid SAR." The ICO has confirmed requests made "verbally, by email, via social media, by post, or in person are all valid," and the one-month response clock starts from receipt "regardless of format." A request "can be made to anyone in your organisation," so "helpdesk staff need training... Any staff member can receive a request, so everyone must know what to do." — [SureCloud: SAR UK GDPR Guide](https://www.surecloud.com/blog-hub/what-is-a-subject-access-request-uk-gdpr-guide)
- **Access vs. erasure are legally distinct rights**: a SAR asks to *access* personal data; the right to erasure ("right to be forgotten") is a separate right under **Article 17 UK GDPR**. Grounds for erasure include: data no longer necessary for its original purpose; consent (the sole legal basis) withdrawn; a successful objection to processing; unlawful processing; or a legal obligation to erase. — [Commoner Law: UK Subject Access & Erasure](https://commoner-law.com/uk/data-privacy-digital-rights/data-subject-access-and-erasure)
- Practical process steps cited: **verify identity** before complying (to stop third parties gaining unlawful access); **escalate/log immediately** to a Data Protection Officer and record in a register (example: the Institute for Fiscal Studies' published Data Subject Deletion Request Policy); **respond within one month**; **do not charge a fee** (the old £10 DPA-1998 fee was abolished when UK GDPR took effect 25 May 2018); **search everywhere** — "A SAR covers any personal data an organisation holds... across all systems, formats and locations. That includes helpdesk ticketing systems and email"; and the response must include purposes, recipients, retention periods and rights, not just the raw data. — [IFS Data Subject Deletion Request Policy (PDF)](https://ifs.org.uk/sites/default/files/2023-08/Data-Subject-Deletion-Request-Policy-latest.pdf), [nibusinessinfo: Dealing with SARs under UK GDPR](https://www.nibusinessinfo.co.uk/content/dealing-subject-access-requests-under-uk-gdpr)
- **2026 UK law change**: under the Data (Use and Access) Act, revised time-limit rules apply to requests received from **5 February 2026**, expressly allowing the clock to pause where clarification is reasonably needed to identify the information/processing concerned. From **19 June 2026**, organisations must also facilitate data-protection complaints — responses should explain how to complain both to the organisation and to the ICO. — [SureCloud](https://www.surecloud.com/blog-hub/what-is-a-subject-access-request-uk-gdpr-guide)
- **Non-compliance route**: individuals can complain to the ICO (ico.org.uk / 0303 123 1113); the ICO does not award compensation — that requires a separate county-court claim under Article 82/DPA 2018 s.168. — [SureCloud](https://www.surecloud.com/blog-hub/what-is-a-subject-access-request-uk-gdpr-guide)
- **Trust & safety triage — hybrid automation/human model**: "Platforms combine automated systems and human reviewers to enforce content policies at scale: before content goes live, proactively after it's live, and in response to reports." Foundever's framework: automation acts immediately on clearly policy-violating content; ambiguous cases go to human moderators; "no single layer is foolproof," so nuanced/novel cases, user flagging, and a clear appeal process all still need humans. — [Foundever: Trust and safety at scale](https://foundever.com/blog/trust-and-safety-at-scale-can-automation-and-ai-deliver-without-human-oversight/)
- Discord's own safety pages (per a fact-check source) say reports are "processed based on priority" via "a combination of automated and human-powered review methods," though the same source notes review times vary and some users report slow or automated-only handling in practice — a caution that a stated hybrid policy doesn't guarantee it works well operationally. — [Do Humans Actually Review Discord Reports?](https://factually.co/fact-checks/technology/do-humans-review-discord-reports-81c81c)
- **Escalation design discipline**: "every escalation flag should be tied to a named decision owner, the evidence behind the flag, an available verdict, the state paused by the escalation, and the event that resumes execution. Without those elements, a flag is only a notification." — [arXiv: Engineering Reliable Coding Agents](https://arxiv.org/pdf/2608.13867) (note: this source is about software-engineering agent oversight generally, not trust-and-safety specifically, but the escalation-design principle is directly transferable and is the clearest statement of it found)
- **Guardrails on automated moderation actions**: recommended practice is that automated actions be "reversible and audited," that "normal users aren't blocked because of one weak signal," and that moderators get explanations and overrides rather than opaque, irreversible automation. — [GitHub issue: trust and safety escalation signals](https://github.com/Rentars/Rentars/issues/635)
- **Regulatory requirement for human review**: both the EU Digital Services Act and the UK Online Safety Act "require statements of reasons for takedowns and meaningful human review on harder calls" where an AI classifier is used to triage reported content (hate, harassment, child-safety violations, violence). — cited within [arXiv: Engineering Reliable Coding Agents](https://arxiv.org/pdf/2608.13867)
- **Signs an automated triage system is failing**: "frequent reopened cases, high analyst override rates, duplicate alerts handled as separate events, and closures that later need escalation." — [nhimg.org: Email triage automation](https://nhimg.org/faq/how-should-security-teams-reduce-manual-workload-in-user-reported-email-triage/)

### Inferences
- Because a valid SAR/erasure request can arrive in *any* wording on *any* channel Freegle uses (Discourse post from a moderator, email to support@/info@, in-app feedback), the intake data model needs a **cross-cutting classification flag** (e.g. "possible data-rights request") that can be raised regardless of which channel or which ticket-type a message otherwise falls into, plus a hard deadline field (one month from receipt, with the 2026 clarification-pause carve-out) — this is a workflow requirement independent of whatever ticket/incident taxonomy is chosen.
- The safeguarding/abuse literature converges on one design rule directly applicable to the brief's "must bypass AI" requirement: any automated triage step (spam filter, auto-categoriser, AI summariser) needs an explicit, cheap **pre-filter for safety/safeguarding keywords or categories that routes straight to a human**, before any AI-assisted drafting or auto-closing touches the message — mirroring the DSA/Online Safety Act "meaningful human review" requirement and the "reversible and audited" guardrail. No source found automates safeguarding-relevant decisions end-to-end; all describe automation for volume/clear-cut cases and hard escalation for anything ambiguous or high-risk.
- "Proxy reporting" (a moderator reporting on behalf of a member) was not directly covered by any source found (see Gaps), but the SAR finding that "a request can be made to anyone in your organisation" and must be honoured regardless of the reporting path implies the same principle should extend to proxy reports generally: the data model should record **both** the reporter (who raised it — e.g. a moderator) and the **subject** (who it is about — e.g. a member) as distinct fields, never conflated into a single "reporter" field, since the two may need different visibility, different follow-up contact, and — in the GDPR case — the "on whose behalf" fact is itself important legally.

### Gaps
- **Proxy reporting** (moderator reporting on behalf of a member) has no dedicated literature found in this search pass — this is a genuine gap; the closest analogues found (VRT's confidentiality-agreement-gated volunteer tier, GDPR's "any staff member can receive a request") are adjacent but don't directly address the proxy-reporting pattern. Worth a targeted follow-up search (e.g. "advocate reporting on behalf of user support ticket" or ombudsman/complaint-handling literature) if this is a priority gap for the final report.
- Did not find literature specifically on **escalation paths distinguishing volunteer-moderator-raised issues from end-user-raised issues** as a first-class design dimension (most trust & safety sources treat "the reporter" as undifferentiated). This is inferred, not cited.
- Did not verify whether the UK's Online Safety Act specifically applies to a platform of Freegle's type/size (it is cited generally as a driver of "meaningful human review" requirements for larger platforms doing content moderation at scale) — this needs a dedicated compliance check outside the scope of this research pass, and should not be treated as a confirmed applicability finding.

## Feedback loops: closing the loop with the reporter, linking tickets to code changes/PRs, changelogs, public status posts; metrics (FRT, resolution time, reopen rate, CSAT)

### Takeaway
The standard pipeline found across sources is: **support ticket → internal issue → PR referencing the issue with a closing keyword → changelog entry linking both → notification back to the original reporter naming the shipped version** — each link is a well-established, separately-documented mechanism (GitHub/GitLab closing keywords, changelog conventions, "close the loop" CX practice), but no single source describes the full pipeline end-to-end; it has to be assembled from parts. On metrics, the four named in the brief (first response time, resolution time, reopen rate, CSAT) are all industry-standard with agreed definitions, but each has a documented gaming risk that a paired counter-metric is meant to catch.

### Cited Findings
- **PR-to-issue linking**: GitHub's own docs specify that typing a closing keyword (`close`/`closes`/`closed`, `fix`/`fixes`/`fixed`, `resolve`/`resolves`/`resolved`) followed by an issue reference (e.g. "Fixes #10") in a PR description "shows that a fix is in progress" and "automatically close[s] the issue when someone merges the pull request." — [GitHub docs: Linking a pull request to an issue](https://docs.github.com/en/enterprise-server@3.0/get-started/writing-on-github/working-with-advanced-formatting/using-keywords-in-issues-and-pull-requests)
- **PR-to-changelog linking, two conventions observed in the wild**: (1) the netcdf-scm project requires one changelog line per merge request linking both the MR and the issue, e.g. "Fixed bug identified in (#YY)"; (2) the Dolibarr project uses a commit-message keyword convention — `FIXED|Fixed #456 Short description` (bug number in upper case so it surfaces in the changelog), with a maintainer compiling the changelog from those commit messages rather than contributors editing it directly. — [GitLab: netcdf-scm](https://gitlab.com/netcdf-scm/netcdf-scm/-/merge_requests/47/pipelines), [Dolibarr commit convention example](https://git.unl.edu/Software_Artifact_Infrastructure_Repository/dolibarr/-/commit/fd1b6444905e258d0b57be85b563fd49cecc7f35)
- **Telling the reporter ("closing the loop")**: "a support rep might see that this customer reported an issue last month, which was fixed in the latest update — all the info needed to craft a meaningful 'we fixed it' email is at their fingertips" once tickets, history, and fixes are linked. A public feedback portal (UserVoice/Canny/a forum) "can facilitate loop closure on a community scale," letting people "upvote ideas and get notified of status changes" — directly analogous to a Discourse-based support/feedback forum. On timing, the recommendation is to "follow up within 24–48 hours of receiving feedback," even just to acknowledge, "because even a quick 'We hear you' buys goodwill until the fix is ready." — [Thematic: Closing the customer feedback loop](https://getthematic.com/insights/close-the-customer-feedback-loop)
- **First Response Time (FRT)**: "the time between when a customer submits a support request and when they get the first meaningful response from the support team." Common enterprise targets: under an hour for email, under a minute for chat — but "customers judge response time against the channel they chose, so one blended target across all channels tends to satisfy nobody." Gaming risk: "replies sent just to stop the clock" — the fix is to only count responses that ask targeted questions or help resolve the issue, not empty acknowledgements. — [Cobbai: First Response Time vs Resolution Time](https://cobbai.com/blog/first-response-time-resolution-time)
- **Resolution Time** = time of resolution minus time of creation, averaged across resolved tickets in a period. Two measurement choices: "customer-inclusive" (counts time the customer themselves took to respond) vs. "internal" (pauses while status = "Pending Customer," measuring only the team's own efficiency). Recommended to report percentiles (P50/P75/P95), not just the average, "to see how spread out resolution times are." — [Cobbai](https://cobbai.com/blog/first-response-time-resolution-time)
- **Reopen Rate** = percentage of resolved tickets that come back within a defined window (commonly 24h/72h/7d/30d — "short windows make the number look better," a gaming risk to watch for). Best practice: tag *why* a ticket reopened (incorrect fix, incomplete data, upstream bug, unclear policy) and count a new ticket from the same requester on the same topic within a few days as a hidden reopen. Related metric, **First Contact Resolution (FCR)**: "strict" FCR requires one agent, one reply, no transfer, no reopen ever; "lenient" FCR counts anything that stayed closed for 7–14 days regardless of how many replies it took. — [Metabase: First Contact Resolution Rate](https://www.metabase.com/metrics/first-contact-resolution-rate)
- **CSAT**: collected via a short 1-question survey right after the interaction, typically 1–5 scale (sometimes 1–10). Formula: (satisfied responses ÷ total responses) × 100, where "satisfied" = 4–5 on a 1–5 scale (or 7–10 on a 1–10 scale) — using total respondents, not total surveys sent. Caveat: "response rates on these surveys are typically in the single digits to low teens, and the answers skew toward the very happy and the furious." — [Simplesat: What is a CSAT score](https://www.simplesat.io/blog/what-is-a-csat-score-definition-formula-tips)
- **Pairing metrics against gaming**: "every metric needs a counter-metric, because any single number can be improved at the expense of another." Suggested pairs: average handle time with FCR; FCR with reopen rate; containment with escape rate; CSAT with response rate. A reasonable minimal set for a small team: **first response time, resolution time, first contact resolution rate, reopen rate, CSAT after closure, and ticket volume per active account.** — [source aggregating these definitions](https://kayako.com/blog/customer-support-metrics/) (general customer-support-metrics guide; specific attribution for the "counter-metric" framing could not be pinned to a single named author across the search results — treat as a widely-repeated industry heuristic rather than one authoritative source)

### Inferences
- Putting the found pieces together gives a concrete, implementable pipeline for Freegle: a Discourse/email/Sentry-originated report → an internal GitHub issue (or the ticket itself, if issue tracking is unified) → a PR using a standard closing keyword against that issue → a changelog line generated from (or linked to) the same issue number → an automated or manual reply to the *original* reporter, on their original channel, naming the release/PR. This is exactly the "linking tickets to code changes/PRs, changelogs" mechanism the brief asks about, and it is buildable entirely from off-the-shelf GitHub conventions plus one new step (notify original reporter) that doesn't exist in any of the vendor tooling found and would need bespoke design.
- Given Freegle's already-fragile mail delivery situation (per this codebase's own findings on Yahoo-family mail), "close the loop" notifications sent by email carry the same delivery risk as any other outbound mail — a public status/changelog post (Discourse category or docs page) is a more robust fallback for closing the loop at the *cohort* level (many people affected by the same known error) even if per-reporter emails are also attempted.
- For a small team, the minimal metric set found (FRT, resolution time at P50/P75/P95, reopen rate with tagged reasons, CSAT after closure) is directly reusable without modification; the main design decision left open is the reopen-window length and whether resolution time should be "customer-inclusive" or "internal" — both are policy choices, not facts to be researched further.

### Gaps
- Did not find a single documented case study of an organisation's *complete* ticket→PR→changelog→reporter-notification pipeline (each piece is well documented separately, but the full assembled workflow is inferred, not directly cited from one source).
- Did not find nonprofit-specific CSAT/FRT benchmarks (e.g., what a "good" FRT looks like for a volunteer-run charity support inbox rather than a commercial SaaS company) — all benchmark figures found are commercial-support-industry figures and may not be an appropriate bar for Freegle.

## Open-source / nonprofit support workflow examples (Wikimedia VRT, Mozilla SUMO) and what they learned

### Takeaway
Both major open-source/nonprofit examples found run support almost entirely through **trusted volunteers**, gated by an explicit trust/vetting step before someone gets access to sensitive tooling or non-public information — Wikimedia's VRT requires a "very good track record" plus a signed confidentiality agreement, and Mozilla's SUMO has no official company support channel at all, running support "scaled by the community." Both also had to deliberately restructure volunteer coordination over time (Wikimedia migrating its ticketing software; Mozilla explicitly renaming "leaders" to "Community Coordinators" after diagnosing problems with informal volunteer hierarchies).

### Cited Findings
- **Wikimedia's Volunteer Response Team (VRT)**, formerly called OTRS after the ticketing software it used, has answered public emails to Wikimedia projects since **September 2004**. Access to the ticket system (VRTS, at ticket.wikimedia.org) is granted only to "volunteers trusted to give courteous, helpful, and accurate responses," who need "a very good track record on Wikimedia projects" and must "sign the confidentiality agreement for nonpublic information." — [Meta-Wiki: Volunteer Response Team](https://meta.wikimedia.org/wiki/Volunteer_Response_Team)
- Incoming emails are **sorted into queues** by the address they were sent to or their subject; roughly **6 admins** (also volunteers) run the queues and manage **400+ agents**. On Wikimedia Commons specifically, VRTS is mainly used to verify and archive copyright/licensing permissions (routed to `permissions-commons@wikimedia.org` or a language-specific address) and to handle copyright-violation reports (`commons-copyvio@wikimedia.org`) — i.e. the queue-routing-by-address pattern doubles as a coarse triage mechanism. — [Commons: Volunteer Response Team](https://commons.wikimedia.org/wiki/Commons:Volunteer_Response_Team)
- The team switched ticketing software from **OTRS to Znuny** in **April 2021** after OTRS's developer discontinued the open-source community edition; the migration is tracked as [Phabricator task T280392](https://phabricator.wikimedia.org/T280392). The team deliberately renamed itself from "OTRS" to "Volunteer Response Team (VRT)" specifically so a future software change wouldn't force another rename — decoupling the *team's name* from the *tool's name*. — [Wikitech: VRT System](https://wikitech.wikimedia.org/wiki/VRT_System)
- Applicants to VRTS are vetted by the small admin group, and there's an explicit screening criterion beyond track record: "almost all tickets come from non-Wikimedians or newcomers, so applicants shouldn't have a history of being harsh with new users" — i.e. the vetting screens for tone/temperament toward newcomers specifically, not just technical competence. — [Meta-Wiki: OTRS/Recruiting](https://meta.wikimedia.org/wiki/OTRS/Recruiting)
- **Mozilla Support (SUMO)**: per a Freshdesk case study, "Mozilla does not have a customer support team, at least not in the official sense — there is no phone line or email address you can use." A Mozilla staffer: "Mozilla Support is scaled by the community." The program covers "content creation and distribution, sharing product updates, vetting content, moderators, raising issues/bugs, and escalating critical reports to the project repository, which is answered by open-source developer contributors" — an explicit path from community-handled support straight into the engineering issue tracker for anything that needs a code fix. — [Freshdesk: Mozilla's Secret to Customer Support](https://freshdesk.com/customer-service-stories/mozilla-blog)
- SUMO's contribution model has five channels: replying to forum posts, writing/translating Knowledge Base articles, and providing support on social media. Localisation is treated as a major, first-class part of the model, "because more than half of all Firefox users speak a language other than English." — [Mozilla-l10n docs: SUMO](https://mozilla-l10n.github.io/localizer-documentation/webprojects/sumo.html)
- **A concrete experiment worth noting**: in 2018 Mozilla ran a time-boxed volunteer sprint (2–9 June) specifically to get volunteers responding to and moderating Play Store reviews of a "technical support nature," because many Android users were reporting problems there instead of through official channels and getting no response — an explicit acknowledgement that users report problems wherever is convenient to them, and support needs to go to that channel rather than assuming users will come to a dedicated inbox. — [Mozilla blog: Support/SUMO event kit context](https://wiki.mozilla.org/Support/SUMO_event_kit)
- **A volunteer-governance lesson**: at a 2017 meeting, Mozilla staff and community representatives agreed "the way we try to organize communities at the moment is not the most efficient and best use of everyone's time, energy, and other resources," citing problems including "inconsistency, competition and conflict, accumulation of power, lack of equal opportunities and oversight." The response was to replace the informal "leaders" framing with "Community Coordination"/"Community Coordinators" roles. — [Mozilla Support Blog, Nov 2017](https://blog.mozilla.org/sumo/2017/11/23/non-coding-volunteers-mission-driven-mozillians-community-coordinators-sumo/)

### Inferences
- Both examples validate a design principle directly relevant to Freegle's moderator-heavy structure: **grant elevated support/ticketing access only after an explicit trust step** (VRT's track-record-plus-confidentiality-agreement gate), and **screen specifically for how a volunteer treats newcomers/vulnerable reporters**, not just technical aptitude — relevant given Freegle's members are often first-time users navigating a local moderator relationship.
- Mozilla's 2018 Play-Store experiment generalises directly to Freegle's channel list in the brief (Discourse, email, in-app feedback, Sentry): rather than assuming reports will arrive at a canonical inbox, the intake design should assume reports legitimately arrive wherever is easiest for the reporter, and the system's job is to pull them into one place — not to funnel people toward a preferred channel.
- Mozilla's governance lesson (informal volunteer hierarchies accumulating power/inconsistency, fixed by explicit "Coordinator" roles with clearer scope) is a cautionary data point for any Freegle design that relies on informal escalation between moderators and the dev team — an explicit, named escalation role/path (mirroring ITIL's Major Incident Manager concept, at a much smaller scale) would likely avoid the same failure mode.

### Gaps
- The brief also named **Mastodon**, **Wikimedia Phabricator** (as distinct from VRT — Phabricator is Wikimedia's separate software development bug-tracking tool), **Discourse's own internal support workflow**, and **Freecycle/Olio** as potential examples; none of these were reached within the tool-call budget for this pass. This is a genuine gap — a follow-up research pass specifically on those four would likely surface additional, possibly more directly comparable, examples (Phabricator in particular, since Wikimedia uses it for engineering-issue triage in a way that might mirror how Freegle's dev team could link Discourse-reported bugs to code fixes). Flagging this explicitly rather than guessing at what those sources would say.
- Existing internal knowledge base notes (`reference_discourse_get_a_room_pair_nudge`, per this session's memory) suggest there may already be Freegle-specific Discourse-support conventions worth cross-referencing, but that is internal/project knowledge, not public web research, and is out of scope for this notes file.
