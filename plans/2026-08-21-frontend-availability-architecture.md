# Keeping the user-facing site up through database cluster problems

Date: 21 August 2026. Research basis: code-level maps of the Nuxt frontend, the Go API, the chat write path and the HAProxy front door; a full inventory and classification of the API's 133 modification handlers; web research (sources at the end) on degraded-mode precedents, event/command sourcing, log-first ingest, file-format practicalities, managed database pricing (August 2026) and Galera vs Patroni availability engineering; candidate designs attacked by adversarial correctness and ops reviews. Companion to `plans/database-migration-evaluation-2026-07.md`, which optimised for schema-change pain and spatial capability; this document optimises for availability.

## 1. Summary

**The brief:** cluster problems regularly leave the front-end site basically broken. Read-write must keep working: people read in order to reply, so read-only mode is useless, and a browser-side outbox is not durability because members close the tab. Batch can be delayed. The direction settled on: an event-source shape where everything ends up as a simple file, and generically for all API modification operations, not as a chat special-case.

**The recommendation: a command log in front of the database, not instead of it.** A middleware in the Go API captures every deferrable modification operation as a command envelope (verified user, route, params, body, a client-stable idempotency key) and appends it to a CRC-framed JSONL file, fsynced, on boxes independent of the DB cluster, BEFORE any database work. On a healthy day the handler then runs unmodified and returns today's byte-identical response; the append costs a couple of milliseconds. When the cluster is frozen or down, the apply step fails or times out, the member gets "accepted" plus their command id, and can close the browser; a projector tails the log and applies the command through the same unmodified handler when the DB returns. One write path, exercised on every request, so the outage path cannot rot. The same pattern the stack already trusts twice: tusd spools uploads to disk before processing, and inbound mail sits in a postfix spool. The web write path is currently the only interactive ingest with no spool.

**Why this is safe for Freegle specifically:** the API's own trust model is already accept-now-check-later. Chat's spam, ban and content checks run in a Laravel cron a minute or two after the insert, and the recipient cannot see a message until that cron has run. Deferring the apply lengthens an existing window; it does not create a new class of unchecked writes, and nothing becomes visible to anyone until the full pipeline has run.

**Scale of the programme:** roughly 14 to 20 person-weeks across all phases (the sum of the per-phase estimates in section 7; the top of the range is dominated by dependent-sequence handling, section 6a), about £50 to £70/month, all engine-agnostic. The first two weeks fix live bugs with standalone value (the API process kills itself on DB blips; chat sends have no idempotency key and duplicate today). The log also hands the committed Postgres migration a shadow-apply and replay-and-diff harness, turning cutover into "repoint the projector". Managed databases were re-costed at August 2026 prices and remain rejected (+£350 to £900/month, a new vendor stack for a two-person team, pay-twice risk against the committed Postgres plan).

**Honest limits, stated up front.** During a full outage the recipient sees the reply when the DB returns; there is nowhere to serve it from until then. What is guaranteed is that nothing typed is ever lost and delivery is automatic, with no member action and no browser open. Login, registration, group creation, payment webhooks and moderation actions stay synchronous by design (deferral is meaningless for them) and still fail when the DB is down. Laravel batch writes the same tables directly and is outside the log's coverage.

## 2. What actually breaks today (measured, with file references)

The availability chain for a member is: Netlify (static app, fine) -> browser calls `api.ilovefreegle.org` directly -> single HAProxy VM (applb) -> Go API running natively on db1/db2/db3 -> Galera cluster. Netlify's CDN is not in the API path at all.

**Cluster-level failure modes** (from the Galera research, with real-world references): flow-control stalls (one slow node pauses commits on every node; ~9 minutes/day measured), TOI DDL freezes (the cause of 32% of schema changes needing manual runbooks), quorum loss (lose 2 of 3 nodes and the survivor refuses everything until a human re-bootstraps), plus SST donor storms and certification conflicts.

**Application-level amplifiers** (each verified by direct code read):

1. **The API process commits suicide on DB failure.** `database/pingDB.go:12-41` runs on every request; on a failed ping it re-inits, and if that fails it calls `os.Exit(1)`. During an outage the first request kills the API on that node; traffic kills all three in seconds.
2. **HAProxy cannot see DB health.** `api_server_backend` uses a bare TCP `check`; there is no `option httpchk` and no `/health` route exists (`/online` returns true unconditionally). A wedged-but-listening API looks healthy.
3. **No timeouts.** No context deadlines reach any GORM query; the cancellation-capable `database.Pool` has zero production call sites.
4. **No cache and no spool anywhere on the web path.** All backends down means HAProxy's generic 503 for every request; applb is a declared, un-remediated SPOF (the second-HAProxy "Option C" design exists in `plans/2026-07-12-katapult-lb-vs-haproxy.md`, unimplemented).
5. **The frontend hangs rather than degrades.** `layouts/default.vue:63` gates all page content on `await bootSession()`; the retry stack can hold a cold load ~75s. The retry stack also retries POSTs up to 10 times with no idempotency key, which is why duplicate chat messages already occur (Discourse 9913) and are cleaned by a nightly fuzzy dedupe cron.

**Chat's shape helps.** In `chat/chatmessage.go:621-1011` the only hard-synchronous write is the `chat_messages` INSERT; ~8 follow-on writes are already best-effort. Recipient visibility already waits for the Laravel cron to flip `processingsuccessful=1`.

## 3. The Netlify question, answered directly

The member site and ModTools are already static Netlify builds; `/message/**` is even ISR-cached as files on Netlify for 10 minutes. The API cannot live on Netlify (Go in Netlify Functions is Lambda-shaped and half-supported; our API is a long-running Fiber process; Netlify DB is a thin Neon wrapper unsuited to a 137GB production database). Batch and mail already fail independently of the site. The split the brief asks for mostly exists; the coupled piece is the API+DB pair, which the command log decouples.

## 4. What the research says (condensed)

- **Log-first is how durability already works everywhere.** Every serious database is a write-ahead log plus a projection; Kleppmann's "turning the database inside out" and the LMAX input journal are the canonical articulations. The proposal applies the same move one layer up, in front of a DB we do not control during its bad days.
- **Command sourcing vs event sourcing matters here.** We log what was asked (the request), not what happened, so replay re-executes handler logic whose reads (bans, membership, reach) may answer differently later. Practitioner consensus is not to reconstruct accept-time state but to make apply-time authoritative. That maps exactly onto Freegle's existing model: checks already run after the insert, at what is effectively apply time.
- **Stale-served reads are the proven outage pattern** (GitHub's 24h read-only mode, Wikimedia's twice-yearly drills), but for Freegle reads surviving is necessary and nowhere near sufficient; the writes-pause half of those precedents does not transfer.
- **File practicalities are well-trodden:** length/CRC framing bounds torn writes to the last record; a single `write()` to an `O_APPEND` fd is atomic; per-record fsync is fine at our under-1-write/s average; segment rotation with closed-segment shipping to object storage is the WAL-G convention; checkpoint = (segment, offset); effectively-once requires the apply itself to be idempotent because a crash replays the last few records.
- **DIY log vs broker, honestly:** NATS JetStream ships the checkpoint/redelivery/DLQ machinery pre-tested and wins past ~2-3 ingest nodes, sustained bursts, or multiple consumers. At our numbers (sub-1 write/s, two ingest boxes, one projector), files are defensible and match the stated values (greppable, rsyncable, no new binary, same family as the maildir/tus spools already in production). The reconsider-trigger is written down in section 6.
- **Managed DB pricing, August 2026:** HA-sized options run ~£650 to £1,050/month vs £420 self-hosted; Neon has no UK region; Aurora DSQL reached London but its restricted surface likely blocks our raw-SQL corpus; PlanetScale MySQL remains the "avoid the ORM rewrite" option if the org ever buys instead of migrates.

## 5. The write surface, measured (whether "generic" is real)

Inventory of `router/routes.go`: **133 distinct modification handlers** (mounted twice, under `/api` and `/apiv2`). Classification:

- **Class A, deferrable** (response is an ack or entity echo; apply may lag): chat send/reply and chat CRUD, roster/typing, MarkSeen, PatchMessage, tryst CRUD, address CRUD, PatchUser/PostUser flags, memberships leave/settings, community events, noticeboards, stories, most admin CRUD, tracking/analytics. **Roughly 85 to 90% of member-interactive core-loop write traffic.** About 60 to 70 handlers are clean CRUD and wrappable by one middleware; the rest of class A hides inside action dispatchers (below).
- **Class B, needs a synchronous DB answer to mean anything:** login/session issuance (returns a JWT), registration (`PutUser`), `CreateGroup`, TN partner membership flows. Deferral is meaningless; these keep today's synchronous behaviour and today's failure mode.
- **Class C, correctness demands synchronous apply:** moderation actions (Approve/Reject/Hold/Spam, chat moderation), account self-deletion, Stripe/PayPal webhooks (the provider's retry loop is the source of truth). Never deferred.
- **Complications found and accounted for:** `message.PostMessage` and friends are action dispatchers multiplexing ~20 heterogeneous sub-actions of mixed class, so the log must wrap at sub-action level there, which is real per-dispatcher work, not free middleware. Envelopes must capture query and path parameters, not just the JSON body (several write handlers read `c.Query()`/`c.Params()`). The LastInsertId-in-response pattern (PutMessage, CreateGroup, PutUser, login) needs one reusable deferred-id contract: healthy apply returns the real id exactly as today; deferred apply returns the client key, which resolves to the id on a later poll. Chat send itself has zero id coupling: `stores/chat.js` discards the POST response and re-polls, so a 202 is indistinguishable from today's ack.
- **Dependent sequences are real and enumerated.** Ten client flows chain a server-returned value into a subsequent call: compose (photo ids -> draft id -> JoinAndPost), chat send with photo (image id -> message), reply-to-post (chat room id -> first message), address (address id -> chat message), community events, volunteering and noticeboard (create -> id -> SetPhoto/AddGroup/AddDate as separate PATCHes, flagged in the code itself as a "server oddity"), plus the anonymous-poster branch where the chained value is newly minted credentials, not an id. Two contradictory attach-photo patterns coexist (photos inside the create body for messages/stories; photos attached after create for events/noticeboards). Section 6a is the handling.
- **Two-writer truth:** Laravel writes `chat_messages` from at least five sites (mail replies, ripple auto-replies, trysts, prompts, background tasks) plus `messages`, `memberships`, `users` from others. The log is therefore a durable record of API-originated commands, not a total source of truth, and the "DB as fully rebuildable projection" endgame is out of reach until batch writers are also captured. That endgame is explicitly deferred.

## 6. The architecture: a command log in front of the database

**Accept path.** Ingest lives in the API middleware, with the log written on boxes independent of the DB nodes: the two HAProxy boxes the front-door phase creates are the natural pair. At accept time, with no DB available or consulted: verify the JWT, check shape and size, apply a file-local per-user rate limit, build the envelope `{command_id (client-stable UUID), userid, route, method, path+query params, body, node_id, accept_ts, prev_command_id for the entity}`, append length-prefixed and CRC-framed to the active JSONL segment, fsync, then call the normal handler. Healthy day: normal response, byte-identical. Handler error or timeout: return `202 {command_id}`.

**Durability mechanics.** One writer per file; torn writes bounded to the last record and detected by framing. Segments rotate on size/age; closed segments ship to Krystal object storage (never the open one). **RPO stated honestly:** fsync survives process crashes; loss of a node's disk loses at most the unmirrored active segment, so rotation is set short (about a minute) and a tail-copy to the peer box shrinks the window further; a dedicated mirror-lag alert exists separately from projector lag. Disk-full fails the request loudly; "accepted" is never returned unless the fsync succeeded. This is stricter than DB-down, deliberately.

**Idempotency is the foundation, and it lives in the database, not in log markers.** The client mints one UUID per logical action and holds it across every retry (the retry stack currently retries POSTs up to 10 times with no key; that is today's duplicate bug). `chat_messages` gains a unique `command_id` column; the apply becomes insert-or-ignore on that key. This single mechanism solves three problems at once: the current duplicate-send bug, double-apply when the API crashes between a successful synchronous apply and anything that could have recorded it (the projector replays, the unique key makes it a no-op), and cross-node dedupe (a retry landing on the other ingest box carries the same UUID; whichever copy applies second is ignored). Set-value PATCHes are replay-safe by nature; increment-style ops are excluded from deferral until keyed. The projector checkpoint is (segment, offset), advanced only after a successful apply.

**Projector.** One owner, one process, reusing the existing handler code path. Throttled catch-up that watches Galera's flow-control metrics while draining, so replay cannot re-trigger the freeze it is recovering from. Bounded retries then a DLQ file for poison commands, with depth alerting. A lag metric that pages loudly. Apply-time is authoritative: a deferred command may be legitimately rejected by checks that would have passed at accept time (membership changed, item taken, user banned mid-outage); that outcome gets explicit "sorry, that is no longer possible" handling, never a silent drop. This is the direct answer to the July evaluation's "unowned projection pipeline fails silently" objection, and the reason this is not a reversal of its CQRS rejection: the log is a transient buffer (retention below), the projection target is the existing DB through existing handler code, and the pipeline has one owner and loud alarms.

### 6a. Dependent sequences: composites first, client keys for the rest

When a flow's later call needs an id the earlier call returns, a deferred head strands the whole chain. Two mechanisms, applied per flow, cheapest first:

**Composite commands where one button press has all the inputs.** Reply-to-post becomes `openChatAndSend(userid, message, firstmsgid)`; community event, volunteering and noticeboard creation each become one `Create...Full` call carrying photo, groups and dates (which also removes the 3 to 5 sequential PATCHes and the redundant refetch after each that these modals do today). Precedent already in the API: `JoinAndPost`. Composites need none of the machinery below, eliminate the chains outright, and are sequenced first (~1.5 pw for all four).

**Client-assigned entity keys for genuinely decoupled chains** (compose photo-then-draft, chat send with photo, address-then-send), where the two calls happen at different moments in different components:

- The client mints one UUID per created entity (for the common single-create command it IS the command_id). Id fields in request bodies keep their types; a sibling `refs` map in the envelope names which fields are unresolved client keys. No `refs` means byte-for-byte today's request, so old clients and the healthy path are untouched.
- A `command_key_map` table (client key -> real id, entity type, minting user, status) is written by BOTH the synchronous handler (same transaction as the create) and the projector, so a mixed healthy/deferred chain resolves regardless of which leg created the row.
- The projector resolves every `refs` entry before calling the unmodified handler, never partially. A command whose references are unresolved is parked in a waiting list keyed by the missing client key and rechecked after each apply; it does not block the log tail. The same rule applies on the synchronous path: a request carrying an unresolved ref is appended and answered 202 even when the DB is healthy, because readiness is gated by dependency resolution, not DB health.
- Ordering needs both graphs: per-entity prev_command_id chains for write-write order on one row, and the refs-derived DAG for cross-entity read-after-write order. Conflating them either over-serialises or loses edit ordering.
- **Cascade policy:** a head rejected at apply time (spam-held, banned, item taken) writes a negative tombstone into the mapping, and the projector auto-rejects all transitive dependents with the same reason, recorded in an outcomes table the client can poll; DLQ is reserved for poison, not understood policy outcomes. Parked commands with no resolution after a generous per-entity-type timeout escalate to the DLQ for a human. The member sees the same rejection copy the synchronous path shows today, just delivered on their next visit.
- Forged references fail in the handler's own unmodified ownership checks, not in the rewrite layer; UUID unguessability is the backstop for the one awkward case (`image.Post` is deliberately unauthenticated for pre-signup posting, so its keys are scoped by session token, not userid). Mapping rows are GC'd on a longer clock (~30 days) than log segments, since a dependent can legitimately resolve tens of hours later.
- **What stays synchronous:** the anonymous-poster JoinAndPost branch returns newly minted credentials; deferring it would strand a plaintext password inside a replayable envelope. It stays class B, failing as today, which also means anonymous posting during a full outage remains unsupported by design.
- **URL story for deferred creates:** no route targets an id that does not exist. The client stays on the success screen ("your post will appear once processed") with a persisted pending state (`sending|pending|applied|rejected`) reconciled against a command-status endpoint on next visit; the one id-based highlight on My Posts is cosmetic and simply skips until resolved.

**Security of accepting without the DB.** A JWT for an account banned moments earlier still gets a 202; the apply-time check rejects it later, consistent with the existing async-check model. The real new risk is flood-to-disk (denial of durability): mitigations are the HAProxy Lua rate limiter already in front, per-user file-local quotas in ingest, body-size caps, disk headroom alerting, and the fact that 202s only happen while the DB path is failing; on a healthy day floods meet the normal DB-backed limits. Replay of captured envelopes is bounded by the command_id uniqueness plus JWT expiry.

**GDPR.** The log is a buffer, not an archive: segments (and their object-storage mirrors) are deleted N days after the projector checkpoint passes them, so PII in the log never outlives the DB copy it fed, and erasure requests are honoured by the DB's existing story plus segment expiry; an urgent erasure can force-delete fully-projected segments early. If the mirror is ever retained for audit instead, that is a separate decision requiring crypto-shredding.

**Read side: files first, cache second.** Hot, shareable reads (per-area browse JSON, message-page JSON) are continuously projected to simple files on object storage/nginx and served as last-good copies when the API/DB path is down; files survive total compute loss, are curlable and diffable, and extend the Netlify ISR file-cache already serving `/message/**`. A Valkey cache remains the fast in-process tier where files are too coarse. Personalised reads (chat lists) stay API-side; files cannot be personalised without becoming a second database. Cached copies carry an explicit last-good timestamp, hard staleness ceilings, and invalidation hooks on delete/withdraw/taken/edit/hold (a known past bug class here).

**When files lose.** Past ~2-3 ingest nodes, sustained multi-node bursts, or a second independent consumer of the stream, the hand-rolled checkpoint/DLQ/merge machinery stops being simpler than NATS JetStream's pre-tested equivalent. That trigger is the point to swap the transport while keeping the envelope, projector and semantics unchanged.

**Migration synergy.** The command log gives the committed Postgres migration a validation harness it otherwise lacks: a second projector applies the same log to Postgres through the ORM-rewritten handlers, state is diffed via the existing "yesterday" replay system, and cutover becomes stopping one projector and repointing, with no big-bang window. The log itself is engine-agnostic throughout.

## 7. Roadmap

Phases 0 and 1 are unchanged prerequisites; the command log is Phase 2, sequenced so every step has standalone value and the critique's "prove idempotency before building the log" ordering is honoured.

**Phase 0: stop shooting ourselves (0.5 to 1 pw, £0).** Replace the `os.Exit(1)` in `database/pingDB.go` with a DB-down flag, per-request 503s and background reconnect; add `GET /health` (designed to distinguish DB-slow from DB-down so a flow-control pause does not flap all three nodes out) and switch HAProxy to httpchk; cap the frontend boot hang by rendering from persisted state while `/session` resolves.

**Phase 1: front door (1.5 to 2 pw, ~+£25-40/mo).** Implement the already-written Option C: Katapult TCP LB in front of two HAProxy boxes. These two boxes double as the ingest pair, so this phase is now load-bearing for Phase 2. Plus `wsrep_desync` on the backup DB node during backups, flow-control alerting, db2 buffer pool raise, db3 back under systemd. (garbd stays dropped: on an odd-sized cluster it changes no quorum outcome.)

**Phase 2a: idempotency, with no log at all (1 to 1.5 pw, £0).** Client-stable UUID per logical send threaded through the retry stack; unique `command_id` column on `chat_messages`; `CreateChatMessage` made safely re-runnable (insert-or-ignore, follow-on writes keyed off the found-or-created row). Fixes the live duplicate-message bug on its own, and is the property everything later presupposes. Includes reconciling the existing fuzzy read-side dedupe so legitimate rapid near-duplicates are not double-suppressed.

**Phase 2b: the log, proven on chat (3 to 4 pw, ~+£10/mo object storage).** Envelope + framing + fsync writer on the ingest pair; rotation, mirroring, mirror-lag alert; the minimal projector (tail, apply via `CreateChatMessage`, checkpoint, DLQ, lag alert, Galera-aware throttle); the 202 path and its frontend states; a scheduled canary that forces a command through the deferred path daily and asserts delivery; a kill-the-projector drill before it is called done.

**Phase 2c: generalise, composites first (6 to 9 pw, £0).** In order: (1) the four composite endpoints (`openChatAndSend`, full-create for events/volunteering/noticeboards, ~1.5 pw) which eliminate three of the seven chains with no new machinery; (2) clean-CRUD class-A handlers by route annotation; (3) sub-action-level wrapping for the dispatcher handlers (~1 week each for the big ones); (4) the section 6a chain machinery for the residual decoupled flows: `refs` envelope field and resolve-or-park in the projector (~1.5 pw), `command_key_map` table and GC (~0.5 pw), cascade tombstones and outcomes table (~1 pw), frontend key minting, pending states and status polling for compose/chat-photo/address (~2 pw). Class B/C stay synchronous, logged for audit only.

**Phase 3: read-side last-good files (2 to 3 pw, ~+£15/mo).** Browse/message JSON snapshots to object storage with the invalidation and staleness rules above; Valkey where speed matters; wired to the same degraded-mode banner (the unused `MaintenanceError` pipeline).

**Phase 4: the engine (already planned, unchanged).** PXC 8.4 now; Postgres+Patroni on the existing programme, now with the log's shadow-apply harness de-risking it. LISTEN/NOTIFY + SSE for chat delivery after cutover.

**Total: ~14 to 20 person-weeks (the sum of the phases above), ~+£50 to £70/month.** It displaces the Postgres programme's start by the same weeks for the same two people; in exchange the site's core loop, including its multi-step flows, survives every cluster failure mode, and the migration itself gets materially safer. If that total needs trimming, the defensible cut line is after Phase 2c step (2): composites plus single-command deferral cover chat, replies and most member actions, leaving only the photo-compose and address chains synchronous-only.

## 8. What we are deliberately not doing, and why

- **Pure-async projection** (every write always a 202, DB applied only by the projector): doubles the felt latency of the 95%+ of requests that would have succeeded synchronously and makes eventual consistency the default rather than the outage behaviour. Log-ahead keeps the healthy day byte-identical.
- **A browser-side outbox as the durability story**: members close the tab. It survives only as the thin supplement for the browser-to-API leg.
- **An outage-only queue behind a circuit breaker** (this plan's own earlier draft): a failure path that only runs during failures rots; log-ahead runs the same append on every request, so the outage path is continuously tested by the healthy path.
- **Stage C, the fully rebuildable-projection endgame**: blocked on two-writer reality (Laravel writes the same tables directly) and not needed for the availability win. Revisit only if batch writes are ever routed through commands too.
- **Managed database / cloud move**: +£350 to £900/month, new vendor stack, provider-scheduled failovers, pay-twice risk against the committed Postgres plan. The one variant worth remembering if the org ever prefers buying to migrating: managed MySQL (PlanetScale Vitess/Aiven/RDS) sidesteps the ORM rewrite.
- **NATS JetStream now**: the trigger conditions (more nodes, bursts, second consumer) are written down; below them, files match the team's values and existing spool patterns. Swap the transport, keep the semantics, if the trigger fires.
- **Local-first sync engines, CDN stale-serve of the API, moving the API to a PaaS**: unchanged rejections (wrong problem, unreliable, and strictly worse respectively).

## 9. Availability outcome, before and after

| Scenario | Today | After Phases 0-3 | After Postgres (Phase 4) |
|---|---|---|---|
| One API/DB node sick or wedged | API process suicide, minutes of 503s; black-hole routing | Auto-failover in seconds via /health; no process death | Same, plus no donor/SST class |
| Flow-control freeze (common, seconds to ~minutes) | Site effectively broken: hangs then errors; sends can take 75s or fail | Reads served (live or last-good); sends logged and applied within moments of the freeze lifting; member sees "sent" and can leave | Mechanism no longer exists |
| Schema change (TOI) | Cluster-wide write stalls; 32% need manual runbooks | Same stalls, masked identically; NBO/RSU where applicable | Transactional DDL, non-event |
| Full cluster outage / quorum loss | Total hard 503, blank pages, typed messages lost | App loads, browse/messages read from last-good files, replies and most member actions accepted durably to the log (member closes the browser), applied automatically on recovery; login/moderation/payments wait | Bounded 25-45s failover instead of unbounded; log masks it |
| applb VM dies | Total outage | LB fails over to the second HAProxy/ingest box | Same |
| Ingest box disk dies | n/a | At most the unmirrored active segment (~last minute) of that box's commands is lost; peer box keeps accepting | Same |
| Chained flow whose head is rejected at apply (spam-held post, taken item) | n/a (fails synchronously) | Dependents auto-rejected with the same reason; member sees today's rejection copy on their next visit, never a silent drop | Same |

## 10. Spikes needed (from the adversarial review, in order)

1. Real fsync latency and durability on Krystal VM disks under load (the design assumes ~1-2ms and true durability; virtio writeback caching could fake both).
2. Idempotent-on-replay `CreateChatMessage` with schema change, built and tested with no log infrastructure (Phase 2a is this spike graduated).
3. Cross-node dedupe proof: a retry landing on the second ingest box must not double-apply against the first box's copy.
4. Galera-aware catch-up throttle, tested against a simulated flow-control freeze.
5. Active-segment RPO measurement plus the mirror-lag alert, distinct from projector lag.
6. `/health` behaviour under a simulated freeze: prove it does not flap the whole pool (Phase 0).
7. Mapping-write/entity-create atomicity under crash (a crash between them leaves an unresolvable client key), and the cross-node resolution race: ingest box A resolves a key while box B's projector has not yet seen A's mapping write (Phase 2c).
