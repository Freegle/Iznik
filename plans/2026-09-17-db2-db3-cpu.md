# db2 and db3 CPU — measured findings and proposed changes

Repeat of `plans/2026-09-02-db2-cpu-reduction.md`, extended to db3. Measured 2026-09-17 from
15:20 UTC.

**Status: findings 1 and 2 are built and awaiting review — PR #1542 and PR #1543. Everything else
in this document is measurement only, and D, H and the db1 read-host change are operator calls.**

Since the last round, PR #1488 (`perf/db2-cpu-reduction`) shipped the reach-mail change feeds, the two keyset purge loops, the illustrations watermark and the leave-check watermark. The reach
recipient query that was 47–68% of db2 on 09-02 is now **2.3%**: the change-feed rewrite in #1488 worked. db2 is
nonetheless in a far worse state than it was, for a reason that did not exist on 09-02.

## Headline

**db2's mysqld is pinned at 7.82–7.88 of its 8 cores (98%), and 53% of that is one query that
used to take 0.29 seconds and now takes 60–74.** The daily digest has not finished inside its
07:00–12:00 window since 2026-09-15; it now runs 24 hours a day and members receive their
morning digest at 01:00. One line of SQL restores it.

db3 is not in trouble: mysqld is at 3.1–3.7 of 12 cores (27%). Its findings are efficiency, not
rescue.

## Method

Unchanged, and the reason for it is unchanged: `events_statements_summary_by_digest` sees
**14.5%** of db2's work. Statement time on db2 is 11,847,970 s, of which the digest table accounts
for 1,713,276 s — Laravel's prepared statements (`statement/com/Execute`, 9,773,022 s) carry no
digest text. Ranking db2 from the digest table gives the wrong answer.

**db3 is the opposite, and this is new information.** There, `statement/sql/select` is 5,395,010 s
against `statement/com/Execute` 408,162 s: db3's traffic is apiv2's Go driver, which sends text
protocol, so the digest table is complete and spans 22 days of uptime. **Every db3 number below is
lifetime, not a sample**, and so is immune to the transient that wrecked proposal G last time.

For db2, ranking is by sampling `information_schema.processlist` in a tight loop
(`analysis/2026-09-17-db-cpu/pl-sampler.sh`, one long-lived connection, `DO SLEEP(0.05)` pacing,
~20 polls/s). Each poll emits at least one row — the sampler's own connection — so idle polls
still count in the denominator. Two companions run alongside it: a per-minute mysqld CPU/load
series, and `longq2.sh`, which stores the **full** text of anything running ≥10 s.

**The sampler answers more than it looks like it does, but it does not watch the whole clock.**
Because it records every poll, `max(time)` per `(connection id, host)` is a TRUE duration for every
statement it saw. That is how both fixes were verified. But it samples in **bursts** - 1,000 polls
at 50 ms, then a 240 s sleep - so it observes only part of the time.

**Measure that coverage before converting any sum into a percentage.** On 09-18 it was **18.7%**
(1,318 distinct seconds observed across a 7,061 s span), so a duty cycle read straight off its sums
is understated by about 5.35x. Counting the distinct second-timestamps in the file gives it:

```
awk -F'\t' '$1+0>0 { ts=int($1); seen[ts]=1; if (ts<mn||mn==0) mn=ts; if (ts>mx) mx=ts }
  END { n=0; for (t in seen) n++; printf "coverage %.1f%%\n", 100*n/(mx-mn) }' db-2-YYYYMMDD.tsv
```

Corrected this way the sampler agrees with `longq2.sh`, which polls every 5 s and so misses almost
nothing: **11.8% against 12.4%** for the spatial rescan, with execution counts of 70 estimated
against ~75 expected. Two instruments built differently landing within 5% of each other is what
makes the number trustworthy; neither alone did.

Ask the sampler first:

```
zcat db-2-YYYYMMDD.tsv.gz; cat db-2-YYYYMMDD.tsv | awk -F'\t' '
  NF>=9 && $6+0>=5 && $9!="" { k=$2":"$4; if ($6+0>mx[k]) mx[k]=$6+0; shape[k]=substr($9,1,40) }
  END { for (k in mx) { s=shape[k]; n[s]++; sum[s]+=mx[k]; if (mx[k]>m[s]) m[s]=mx[k] }
        for (s in n) printf "%5d %5d %7d  %s\n", n[s], m[s], sum[s], s }' | sort -k3 -rn
```

Five traps, all hit during this run and all worth writing down:

- `mysql -B` escapes tabs and newlines in data, so split output on the two-character `\t`.
- MySQL strips `/*comment*/` from `processlist.INFO`, so a sampler cannot tag its own row with one.
- Replaying a captured statement into `EXPLAIN` **after** flattening its newlines silently
  truncates it at the first `--` comment. Capture with a newline placeholder and restore it.
- **A capture that writes one row per connection id records a FLOOR, not a duration** - whatever the
  statement had reached when a poll first caught it. Append every sighting and take the max.
- **Escapes written into a source file may arrive as real bytes.** A test full of U+200F literals
  made Go refuse the file with "illegal byte order mark". Build such characters from code points.

# Findings

## 1. The daily digest carryover broke the index — 53% of db2

`UnifiedDigestService::getPostsForUser()`, `iznik-batch/app/Services/UnifiedDigestService.php:2151`, the `OR` at `:2205`.

`7aa3477148` ("posts the cap left out are offered again in the next digest") added a carryover list
to the window predicate:

```php
$q->where('messages_groups.arrival', '>', $tracker->lastmsgdate);
if ($carryover !== []) {
    $q->orWhereIn('messages.id', $carryover);      // <- this
}
```

The `OR` reaches a **different table** from the range column. MySQL cannot index-merge across
tables, so it abandons the `groupid (groupid, collection, deleted, arrival)` index and, because the
query is `ORDER BY messages_groups.arrival ASC LIMIT 500`, falls back to walking the `arrival`
index from the oldest row forward — all 11,037,181 of them — running five dependent subqueries on
every candidate.

Measured on db2, same member, same moment:

| form | `EXPLAIN` | time |
|---|---|---|
| as shipped | `type: index`, key `arrival`, filtered 5% | **60–74 s** (observed live; 8 concurrent) |
| `FORCE INDEX (groupid)` | `type: range`, key `groupid`, 407,246 rows, `Using index` | **0.59–1.23 s** |
| carryover arm removed | `type: range`, key `groupid`, **1,514 rows**, `Using index` | **0.24–0.31 s** |
| carryover arm alone | primary-key `IN` of ≤65 ids | **0.21–0.43 s** |

**24,428 of 450,588 digest trackers (5.4%) carry a non-empty list**, mean 65 ids, max 415. At 60 s
each across 8 shards that population needs 50.9 hours; the window is 5.

### The date is exact

`UnifiedDigestDaily` sends, from `email_tracking`:

| day | sent | first | last |
|---|---|---|---|
| 09-13 | 66,632 | 06:00:38 | 10:59:48 |
| 09-14 | 66,525 | 06:00:58 | 10:59:18 |
| **09-15** | **52,426** | 06:00:40 | **23:59:59** |
| 09-16 | 64,529 | **00:00:01** | 22:58:30 |
| 09-17 | 36,187 (to 15:34) | 06:00:36 | still running |

Hourly, 09-14 was 31,790 + 31,941 + 2,645 and done. From 09-15 it is 2,000–6,000 per hour, all day
and all night. **Throughput fell 13×.**

The feature reached master at 09-13 10:03 (PR #1497 carried it in) and `batch-prod` bind-mounts the
working tree, so it went live immediately. The 09-14 run **wrote** carryover and **read** none, so
it was normal. The 09-15 run was the first to read one. One day's delay, exactly as the mechanism
predicts.

Right now, all eight `mail:digest:unified --mode=daily` shards have been running since 06:00:30
UTC — 9.5 hours into a 5-hour window — and the sampler finds 7.40 of them inside this query at any
instant. **Those eight processes are db2's saturation.**

### Fix

Two tiers, and the cheap one is available immediately:

1. **`FORCE INDEX (groupid)` on the `messages_groups` join.** One line, no semantic change (the
   `whereIn('messages_groups.groupid', …)` that makes the index applicable is already there and
   applies regardless of access path). 60–100×.
2. **Split the two arms.** Fetch the window (`arrival > cursor`, `LIMIT 500`) and the carryover
   (primary-key `IN`) separately, merge, sort by arrival, take `DIGEST_LOAD_CAP`. 200–250×, and it
   keeps the good plan whatever the optimiser decides later.

The split was checked against the shipped query on live data: **identical row sets, 756 = 756, zero
rows on either side of the difference.**

**One pitfall, found by checking rather than reasoning.** The raw multisets are *not* equal —
1,921 rows against 1,687. The 234 extra are carryover posts that also satisfy `arrival > cursor`
and so come back from both arms. A SQL `UNION` de-duplicates them; two PHP queries must
de-duplicate on the **(msgid, groupid) pair**, not on msgid, because the query returns one row per
copy of a cross-posted item.

### Also worth a test while this is open — not measured, from reading the code

`updateDigestTracker()` sets the cursor from `$posts->last()`, and `$posts` is ordered by arrival
ascending. The docblock argues carryover posts "come first in arrival order and the cursor never
moves backwards for them" — true only while the window also contains a newer post. When a run
returns **carryover alone**, `last()` is a carryover post, whose arrival is older than the cursor
by construction, and `lastmsgdate` **regresses**. The live cursor that produced the query timed
above was `2026-09-14 09:11:34`, exactly `CARRYOVER_MAX_AGE_DAYS` back.

That is suggestive, not proof — an overdue member looks the same from outside. It is cheap to
settle with a unit test (fabricate a tracker whose window has only carryover, assert the cursor
does not move backwards) and it should be settled before A is written, because a regressing cursor
widens the window that A is making cheap.

## 2. The rippled-then-left suppression scans 22.4 M log rows per candidate group — ~12% of db2

`ExpandService::rippleIntoNewGroups()`, `ExpandService.php:1838`; the target-group selection for
crossposting, with the offending `NOT EXISTS` inside the statement starting at `:1915`.

**This is not the leave-check #1488 fixed.** That watermark is at `:2332`, in the separate sweep
that pulls copies back when a poster leaves. This is a different query in a different method and
is untouched by it.

One execution was observed running for **1,022 seconds** and was present in 100% of 3,000 polls —
a continuous core, 12.5% of db2. `EXPLAIN` on the captured statement:

```
4  DEPENDENT SUBQUERY  lj   index_merge  Using intersect(type,user)       11,514 rows
4  DEPENDENT SUBQUERY  ll   ALL          Range checked for each record  22,432,606 rows
4  DEPENDENT SUBQUERY  lj2  ALL          Range checked for each record  22,432,606 rows
```

Two full-table scans of `logs` (22,421,444 rows, 5.8 GB) re-decided per row, inside a correlated
`NOT EXISTS` evaluated per candidate group. This is the same failure mode as the microvolunteering
stall of 09-13: *Range checked for each record* over millions of rows, no error, no warning, just a
query that never ends.

`logs` has `groupid`, `user` and `(type, subtype)` as separate indexes and nothing composite, so
the `ll`/`lj2` arms — correlated on user, groupid, type, subtype **and** `id > lj.id` — have
nothing to use.

### Fix

The whole check is "for this one poster, is their most recent ripple-join to this group followed by
a leave?" It is per (user, group) and the user is constant for the entire call. Fetch it once:

```sql
SELECT groupid, subtype, text, id FROM logs
 WHERE user = ? AND type = 'Group' AND subtype IN ('Joined','Left')
```

Measured on db2 for the poster in the captured statement: **0.10–0.61 s, 15 rows.** Decide in PHP.

An index on `logs (user, groupid, type, subtype, id)` would also fix the plan, but it is operator
DDL on a 5.8 GB table under Galera, and the code fix is better: it removes the scan rather than
making it affordable.

## 3. db1 serves member traffic and reads from db2 — measured, and NOT worth acting on

`MYSQL_HOST_READ` on db1's apiv2 is `10.220.0.150` = db2. On db3's it is `10.220.0.47` = itself.

Live, not inferred: `ss` on port 8192 shows **48 established connections from applb (185.199.221.13)
on db1** and 67 on db3 — member API traffic is split roughly 42/58 between them, and db1's share of
the reads lands on db2. db2's own apiv2 has **zero** connections, so essentially all of the
plain-`SELECT` traffic on db2 is db1's.

The repo's `haproxy/haproxy.cfg` still marks db1 and db2 `backup` with db3 the only active apiv2
backend. **The deployed applb does not match the file.** That drift is worth fixing on its own
account; it is what made this look like a post-deploy transient last time.

**The size of it: 14.4% of db2's statement time over 27 days, about 0.56 of its 3.88 cores.** Plain
`SELECT` is 1,706,885 s of 11,847,970 s.

**That is not a lever, and an earlier draft of this document was wrong to present it as one.** It
quoted 27.9%, from thread share in a 30-minute sample of a saturated node — which measures
queueing, not work. Against findings 1 and 2 (three quarters of db2 between them, measured) 0.56 of
a core does not justify touching production routing.

It is also not a misconfiguration. db1 is a deliberate standby, kept for a node failure and for
taking backups; being in the pool is part of what makes it able to take over. The reads going to
db2 are just the app-level write-funnel convention applied to it.

**The method note is the part worth keeping: rank a saturated node by statement time, not by thread
share.** The two disagreed by 2x here. The 09-02 round was burned by a post-deploy transient; this
round was nearly burned by a queue.

# db3 findings

db3 has no emergency. Its mysqld uses 3.1–3.7 of 12 cores and nothing runs long. What follows is
where its work goes.

## 5. The same feedback count is asked for twice — 5.3% of db3

`session/session.go:1500` totals it; `group/groupWork.go:357` groups it by group. Same table, same
cutoff, same group set, same eleven `comments !=` exclusions. **1,299,372 + 1,334,035 = 2.63 M
executions**, 122 ms and ~41,000 rows examined each, 322,021 s of db3 (plus 136,792 s on db2 from
db1's apiv2). The total is the sum of the per-group counts; one query can serve both.

**And they do not agree.** `groupWork` has `AND mo.comments != ''`; `session` does not. The comment
in `session.go` says the aggregate "must match the per-group badge". A feedback row with an
empty-string comment is counted by one and not the other. Folding them into one query fixes the
inconsistency as a side effect.

## 6. Browse's spatial queries are db3's largest area — 24.2%

Six shapes of `messages_spatial` feed/count total 1,475,030 s. The largest single one is 569,427
executions at **637.7 ms**, examining **217,594 rows to return 1,400**. These are member-facing
browse requests, they are all under a second, and there is no defect visible in them — the cost is
in the volume and the ratio. Worth a design look, not a fix; noted so the next round does not have
to rediscover the ranking.

## 7. The newsfeed reads most of the table per request — 13.5%

Two arms, both `FORCE INDEX`:

| arm | execs | avg | rows examined | rows sent |
|---|---|---|---|---|
| `FORCE INDEX (timestamp)` (no location) | 7,288,021 | 79.6 ms | 8,202 | 100 |
| `FORCE INDEX (position)` (located) | 1,195,475 | 201.6 ms | **166,712** | 52 |

`newsfeed` holds **180,148 rows**. The located arm examines 93% of the table to return 52 rows,
1.2 M times. Both are flagged `no_index_used` on 100% of executions. The timestamp arm's
`OPEN_AGE_CHITCHAT` backstop is doing its job (8,202 rows); the position arm has no equivalent
bound once `MBRContains` fails to narrow.

Also worth noting for whoever picks this up: 86% of newsfeed requests arrive with **no location**
and take the timestamp arm — consistent with the "Anywhere" default.

## 8. Email open tracking — 6.6% of db3, all of it writes

`INSERT INTO email_tracking_images` runs **50,643,850 times** (203,453 s) and the `opened_at`
`UPDATE` 9,276,209 times at 16.52 ms (153,268 s). `emailtracking.go:361` writes an image-load row
unconditionally on every pixel fetch, forever; `email_tracking_images` holds 7.38 M rows against
50.6 M inserts in 22 days, so something is purging ~3 days behind.

This costs db3 only — finding 0 above shows replication apply is ~1% of a core, so it does not
touch db2. Whether 2.3 M image-load rows a day is worth 6.6% of the write node is a product
question, not a bug.

## 9. Admin group-list statistics take 25 seconds

`group/group.go:584–605` fires three parallel 31-day aggregates whenever an admin or support user
loads the group list. The `logs` one averages **24,763 ms** over 2,204,480 rows. Only 720
executions in 22 days, so 17,829 s — negligible as CPU, but it is a 25-second page for the people
who use it most, and each one holds a connection for the duration. Cache it, or roll it up with the
other nightly stats.

## 10. Embedding search group lookup — ~1% of each node

`embedding/store.go:156` fetches `messages_groups` for the candidate msgids a semantic search
returns: 195,390 rows examined per call, 1,588 ms, 13,132 calls on db3 and 26,237 on db2
(1,906 ms) — about 71,000 s across the two. The `IN` list is large enough that the `msgid` index
stops paying. Batch it, or push the collection/deleted filter into the embedding store.

The two single-window figures each have an independent structural corroboration (eight shards

## Deployed 2026-09-17 19:13 UTC — what it actually did

#1542 and #1543 merged and pulled. batch-prod bind-mounts the working tree, so the code was live at
once for any NEW process — but PHP loads code at process start, and the eight daily shards had been
running since 06:00:30. `PreventsOverlapping` is keyed per (mode, shard), so tomorrow's 06:00 ticks
would have logged "Already running, exiting" and the fix would never have taken over. They were
cycled. The lock is a real `flock` with `LOCK_NB`, released on process death, so nothing was stale.

**Killing those eight alone took db2 from 7.85 cores to 2.00.** That is the cleanest measurement in
this document: they were ~5.85 cores, about **75% of the node** — more than the 53% the thread
sample suggested, because everything else was queueing behind them and its own thread count was
inflated too. Load average fell 12.4 -> 5.6.

Today's remaining recipients were then sent on the new code, rather than left to tomorrow's
catch-up. The once-per-London-day guard (`UnifiedDigestService.php:1745`) excludes anyone whose
`lastsent` is already today, so the re-run picked up exactly those still owed, with no duplicates.

| | before (old code, pinned) | after (new code) |
|---|---|---|
| send rate | ~2,500/hour | **28,020/hour** |
| db2 mysqld | 7.85 / 8 cores | **4.67 / 8 cores** |

**11x the throughput on 60% of the CPU**, and back to the pre-regression rate (~32,000/hour on
09-14). For comparison, the healthy 09-14 run cleared the whole population between 06:00 and 08:00.

## Why three days of this surfaced nowhere — PR #1544

Worth recording, because one of the three layers WAS watching and reported healthy.

**Sentry: nothing to catch.** No exception was thrown — the query was slow, not failing, and every
shard reported `Errors: 0`. The digest is also deliberately excluded from `sentryMonitor()`
(`routes/console.php:462`): a job whose cron expression says `everyMinute` but which is gated
`->between(7,12)` and `->withoutOverlapping()` would raise a missed check-in every minute of the
other nineteen hours. **9 of 147 scheduled commands have a Sentry monitor, and none is in the mail
pipeline.**

**The outcome monitor: it ran, and it passed, every day.** This is the mechanism that comment
points to instead of Sentry, and the daily digest IS registered and IS enabled
(`daily_allowlist = '*'`). But it is a `ProducedSinceCheck` with
`digest_daily_min_expected = 1` — "was at least one digest sent today?". 40,000-52,000 were. It is
a liveness check being read as a health check.

**ModTools: digest click-through analytics only.** Nothing on throughput or completion.

**The signal was in the column the check already reads.** `lastsent` for mode=daily, against the
window the job is scheduled in:

| day | sends after 12:00 London | would the window check fire? |
|---|---|---|
| 09-13 | 0 | quiet |
| 09-14 | 0 | quiet |
| **09-15** | **34,031** | **FIRES — first broken day** |
| 09-16 | 33,157 | FIRES |
| 09-17 | 27,402 | FIRES |

A volume floor was considered and rejected: any figure is a guess off one week's traffic, has to be
loose enough to survive a quiet day, and is therefore too loose to catch a 2x slowdown. The window
comes from the schedule and needs no tuning.

**The general lesson, which is not specific to the digest:** a floor of 1 on a job that produces
tens of thousands of rows asserts only that the job is alive.

The registry has exactly two `ProducedSinceCheck` entries and **both** have a floor of 1. The other
is `stats_daily_min_expected`, "Per-group daily stats rows generated for yesterday", against a real
daily volume of **~4,300 rows** (09-13 to 09-16: 4,332 / 4,395 / 4,278 / 4,285). If stats generation
fell to a single group it would pass, exactly as the digest did.

Not fixed here, because the right floor is a derived one rather than a guessed one — the row count
should track the number of published Freegle groups, which is knowable from the database — and that
is a different change from this one. Recorded so it is a decision rather than an oversight.

## Post-fix monitoring: the spatial reconcile re-scans 31 days every 5 minutes

Found by lowering the long-query capture from 45s to 10s once nothing legitimate exceeded a second.
At the old threshold it was invisible.

`messages:update-spatial-index` (`routes/console.php:1294`, `MessageSpatialService.php`) runs
`->everyFiveMinutes()` and re-reads a **31-day** window of `messages_groups` on every run
(`RECENT_DAYS = 31`), joining six tables under a DISTINCT, to find the few rows whose
`messages_spatial` copy has drifted. One execution measured at **16 s**.

**Two things tested and rejected, so nobody repeats them:**

The optimiser picks the `collection` index (9,224,506 rows matching `collection='Approved'`)
over `arrival` (634,414 rows for the 31-day window), which looks like a 14.6x waste.
`FORCE INDEX (arrival)` does change the plan to a range scan - and the query still takes
**15.65 s and 14.09 s against ~16 s**. The index choice is not the cost. The cost is the per-row
work after filtering: ~630k surviving rows times six lookups, two of them correlated `NOT EXISTS`
arms (`newer_outcome`, `better`), plus a temporary table for the DISTINCT.

**Measured: ~12% of one core**, by two instruments that agree. `longq2.sh` (5 s polling) gives
12.4%; the sampler gives 2.2% of the time it watched, which is 11.8% once corrected for its 18.7%
coverage. Execution counts reconcile too: 70 estimated against ~75 expected at one per 4.6 minutes.
Longest seen, 49 s after the fixes and 89 s before them.

### How this number was wrong four times, and what that is worth

| | figure | basis | why it was wrong |
|---|---|---|---|
| first estimate | ~5% | one first-sight capture | duration was a floor |
| structural inference | 10.7% | reading `updateSpatialIndex()` | assumed both heavy scans ran long |
| "corrected" count | 5.2% | 24 first-sight captures | same floor, more of them |
| re-measured | 12.4% | 7 true durations, 30 min | **right, but not yet trusted** |
| "corrected" again | 2.2% | 13 true durations, 5.8 h | sampler sums divided by WALL-CLOCK span |
| **confirmed** | **~12%** | **two instruments, reconciled** | — |

Five of the six figures were wrong, and they share one cause: **a denominator that did not match
the numerator.** First-sight durations over true elapsed time; a burst window over a daily rate;
and finally sampler sums - covering 18.7% of the clock - divided by the whole clock. The last one
is the sharpest, because by then the durations were real and the arithmetic still went 5x wrong in
the opposite direction to the previous error.

What settled it was not a better single measurement but **two instruments built differently landing
within 5% of each other**, with their execution counts agreeing independently.

The first version of `longq.sh` wrote one row per connection id and skipped that id thereafter, so
it stored whatever `time` the query had reached when a poll first caught it above the threshold -
not how long it ran. The CPU watch saw 43 s where that file recorded 19 s.

**The instrument that was right all along was the processlist sampler.** It records every poll, so
`max(time)` per connection id gives true durations, and it had been running since 15:23. Two
purpose-built capture scripts were written and debugged before anyone thought to ask the sampler.
Check what you already have before building a second thing to measure it.

it stored whatever `time` the query had reached when a poll first caught it above the threshold -
not how long it ran. The CPU watch saw 43 s where that file recorded 19 s. **Every duration it
captured is a floor**, so the 24-sample count of 5.2% was too low by more than half.

The instructive part is which method won. The structural inference - read the code, reason about
what runs - landed at 10.7%, nearest the truth. It was dismissed in favour of a count, on the
principle that counting beats reasoning. That principle is right and the application was wrong,
because the count came from an instrument measuring something other than what its column name
implied. **Check what your counter records before you trust it over your model.** The frequency it
reported (one every 4.6 minutes) was correct throughout; only the durations were not.

`longq2.sh` replaces it from 00:05: it appends EVERY sighting, and analysis takes `max(time)` per
connection id. Validated by running a known 14 s query and confirming three rows at 12 s, 17 s and
22 s - a climbing series for one statement, which the old version could not produce.

It cannot account for the periodic 5-core readings, because one query occupies one core.

**The wider picture.** With true durations, every production query over 10 s across 00:05-00:35
totals 9 executions and 262 s - **14.4% of one core**, of which the spatial reconcile is 12.4
points. (The earlier figure of 7.4% over a longer window came from the same first-sight floors and
is likewise too low.)

The shapes below were identified from the first capture; the counts and maxima are from it, so read
them as relative weights rather than durations:

| shape | n | max | what it is |
|---|---|---|---|
| spatial reconcile | 24 | 19 s | `MessageSpatialService` - this finding |
| search index build | 4 | 18 s | `MessageSearchService`: `msgid NOT IN (SELECT msgid FROM messages_index)` over the 31-day window |
| search embedding backfill | 2 | 18 s | `GenerateSearchEmbeddingsCommand`: `users_searches` LEFT JOIN embeddings, six months back, `LIMIT 100` |
| EEE classifier | 2 | 16 s | `EeeClassifyNewCommand`: Offers with `NOT EXISTS (messages_eee)` |
| chaseup / autorepost | 2 | 12 s | `AutoRepostService` / `ChaseAdminCommand`, with `TIMESTAMPDIFF(HOUR, arrival, NOW())` |
| active-user scan | 1 | 10 s | `users`, `deleted IS NULL AND lastaccess >= ?` - **proposal D**, first direct timing |

Every one of them is an antijoin or an outer join looking for "rows without a partner", over a
window measured in weeks or months, on a schedule. That is the same shape as the four jobs #1488
put a keyset watermark on, and as findings 1 and 2. It is the house pattern for slow batch work
here, and worth checking for first in anything new.

None of them is individually worth chasing at 7.4% of one core between them. Listed so the next
round starts from names rather than from query text.

**Caveat for whoever reads the capture file:** it records every slow statement including diagnostic
queries run by hand. A 13 s `select "rows matching collection=Approved"` at 21:16 is one of those,
not production work.

The fix shape, if it earns its place, is the keyset watermark #1488 applied to four other jobs that
had this same pattern: drive from what changed rather than re-examining a month. The payoff here is
smaller than any of those, so it is a candidate and not a priority.

## Both fixes verified from the sampler, before against after

The processlist sampler records every poll, so `max(time)` per connection id is a true duration.
Split at 19:13, when #1542 and #1543 went live. Queries reaching 5 s or more, on db2:

| shape | before, 15:23-19:13 | after, 19:13-01:00 |
|---|---|---|
| ripple target-group (#1543) | max **1,364 s**, **~173% of one core** | **absent** |
| digest `getPostsForUser` (#1542) | max **101 s**, ~28% | **absent** |
| spatial reconcile | max 89 s, ~55% | max 49 s, ~12% |
| active-user scan (proposal D) | max 38 s, ~38% | max 12 s, ~12% |
| `SELECT COUNT(*), groupid FROM ...` | max 94 s, ~16% | absent |

Percentages are corrected for the sampler covering 18.7% of the clock; the raw observed sums are
4,454 / 725 / 1,419 / 992 / 405 s before and 458 / 475 s after. Over 100% means more than one copy
ran at once, which the ripple query did.

**Both fixed queries vanish from the slow population entirely** - not reduced, absent. That is the
cleanest verification in this document, and it needed no new instrument.

Two things fall out of it that were not visible before:

- The ripple target-group query reached **1,364 seconds** - 22.7 minutes, well beyond the 1,022 s
  quoted in finding 2 and the single worst statement recorded all evening.
- Everything else got faster too. The active-user scan went from max 38 s to max 12 s, and the
  spatial reconcile from 89 s to 49 s, with no change to either. They were queueing behind the two
  bad queries. **On a saturated node every caller looks slow**, which is the same lesson the
  thread-share error taught, arriving from the other direction.

## Finding: purge:chats scans 20.5 M rows on the WRITE node to delete six

Caught at 02:04 by the long-query watch - the first statement over 60 s on db3 all night, at
**266 seconds**:

```
delete from chat_messages where date < 2026-09-11 02:00:26 and reviewrejected = 1 limit 1000
```

`PurgeService::purgeSpamChatMessages()`, scheduled `dailyAt(02:00)`.

| | |
|---|---|
| `chat_messages` | 40,946,105 rows, 5.9 GB |
| plan | `range` on the `date` index, **20,474,759 rows**, filtered 10% |
| index on `reviewrejected` | **none** - the table has `reviewrequired`, not `reviewrejected` |
| rows actually deleted, 09-17 | **6** |
| rows to delete tonight | **0** |

So it walks half the table to find nothing, and did the same yesterday to find six. Because the
loop condition is `while ($deleted > 0)`, a run that deletes anything at all pays for a second
full scan to confirm the third is empty.

**This is the defect #1488 fixed, in a third loop in the same file.** `purgeEmptyChatRooms`,
immediately below it, carries a keyset watermark and a comment reading "for the same reason as
purgeOrphanedUserLogs". `purgeSpamChatMessages` did not get one. That is the second miss of this
exact shape tonight: #1543 fixed `rippleIntoNewGroups` after the identical rewrite had been applied
to `addPosterMembershipToRippledGroups` on 08-31 and stopped there. **When one call site is fixed,
grep the file for its siblings.**

**Why it is on the write node and why that matters more than the CPU.** This is a DELETE, so it
runs on db3, and it held a transaction open for four and a half minutes. Under Galera a long write
transaction is a certification risk, not merely slow. The CPU cost - roughly 4 minutes of one core
a day - is the least of it.

### Three fixes, and why none of them is obviously right

1. **Index `chat_messages (reviewrejected, date)`.** Turns the scan into a lookup. But it is
   operator DDL on a 40.9 M-row, 5.9 GB table which cannot take INSTANT ADD (see
   [[reference_chat_messages_compressed_ddl_rename]]), so it is a full rebuild on a Galera node.
2. **Keyset watermark within the run, copying the sibling.** Stops later chunks rescanning from the
   start - but the common case here is ZERO rows to delete, where a single id-ascending pass still
   walks the whole table before concluding. It fixes the wrong half.
3. **A watermark that persists ACROSS runs**, like `ripple_leave_check_last_log_id`. Each run then
   examines only the band that crossed the 7-day cutoff since the last run. This is the real fix,
   and it carries a correctness question that is not mine to answer: a message rejected *after* the
   watermark passed its id would never be purged. Whether review always happens well inside seven
   days is a moderation-timing question.

Left for a decision. The cheap half of (2) - changing `while ($deleted > 0)` to stop when a chunk
comes back short - halves the cost on any day that deletes something, is behaviour-preserving, and
needs no judgement about anything.
